## Design System

| Property | Value |
|----------|-------|
| Tool | none |
| Preset | not applicable |
| Component library | antd v6 (existing — `frontend/package.json`, `antd ^6.3.0`) |
| Icon library | none — hand-rolled glyphs/shapes (unicode `✓`/`⏳`/`—` in `StatusChip`, CSS-drawn circles in `CountPill`); Phase 16 continues this, no icon package added |
| Font | Rubik (existing — `frontend/src/lib/theme.ts` `fontFamily`, applied inline across every route) |

**Why "none" and not shadcn:** this is not a greenfield frontend — it's an established, five-phase-old production app with its own working design system (antd v6 + a custom `ThemeConfig` in `theme.ts`, consistently applied via inline styles across `report.tsx`, `admin.heatmap.tsx`, `assessments.tsx`, `dashboard.tsx`). Introducing shadcn/Tailwind now would fragment the UI into two unrelated component systems for zero benefit — Phase 16 extends the existing system instead. `components.json`/`tailwind.config.*`/`postcss.config.*` all confirmed absent from the repo root.

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon/dot-to-label gaps (band dot ↔ dimension name) |
| sm | 8px | Compact spacing — table cell padding, chip/badge internal padding |
| md | 16px | Default element spacing — card padding, row gaps in priority list |
| lg | 24px | Section padding — gap between radar-chart card and priority-list card |
| xl | 32px | Layout gaps — gap between report header and content, admin org-summary vs per-initiative table |
| 2xl | 48px | Major section breaks — not expected to be needed at this phase's scale, reserved |
| 3xl | 64px | Page-level spacing — outer page padding on wide viewports (matches existing `report.tsx` `padding: "2rem"` ≈ 32px, keep at 32px not 64px for consistency) |

Exceptions:
- `controlHeight: 44px` (buttons/inputs, existing `theme.ts` token) — carried forward, not a new exception.
- Legacy off-scale inline values already in the codebase (`gap: "6px"` in `StatusChip`, `padding: "10px 16px"` in heatmap headers, `padding: "14px"` in `NextStepsPanel`) are pre-existing and **not** to be copied into new Phase 16 code — all new elements built this phase (radar-chart card, priority-list rows, admin per-initiative table, band legend) use only the scale above.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px | 400 | 1.5 |
| Label | 13px | 400 | 1.4 |
| Heading | 20px | 600 | 1.2 |
| Display | 28px | 600 | 1.2 |

Usage:
- **Body (14px/400):** priority-list dimension descriptions, admin table cell text, band legend caption text — matches the dominant `0.875rem` size already used across `report.tsx`/`assessments.tsx`.
- **Label (13px/400):** small meta text — "Based on N submitted initiatives", per-row score value labels, table column headers.
- **Heading (20px/600):** card/section titles — "Maturity radar", "Priority areas", "Per-initiative breakdown" — matches the existing `1.25rem`/600 card-title pattern (`NextStepsPanel`, `assessments.tsx` card H2s).
- **Display (28px/600):** page-level title — "Your DSSC Maturity Report", "Aggregated Maturity Overview" — matches the existing `1.75rem` H1 size (`assessments.tsx`, `admin.heatmap.tsx`).

Only two weights are declared for this phase's new elements: **regular (400)** and **semibold (600)**. Note: some pre-existing route-level H1s (`assessments.tsx`, `admin.heatmap.tsx`) use weight 700 — that is a legacy artifact predating this contract; do not replicate 700 in new Phase 16 elements, standardize on 600 for all new headings/display text.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#ffffff` | Card/content surface backgrounds — the radar-chart card, priority-list card, admin per-initiative table card |
| Secondary (30%) | `#06004f` (navy) | Header bars atop chart/table cards (matches existing `HeatmapMatrix`/`HeatmapGrid` navy header-row precedent), page-title text, section headings, primary button fill |
| Accent (10%) | `#399e5a` (brand green) | Reserved for: the "Mature" (green) maturity-band dot/label only, link color (`colorLink`), and hover/success confirmation states — **not** used as a generic decorative color |
| Destructive | `#ff4d4f` (antd default danger) | Error `Alert` components, any future destructive action — deliberately distinct from the maturity-band red below to avoid "delete/error" and "low maturity score" reading as the same signal |

Accent reserved for: the green maturity-band indicator, `colorLink` text links, and success/hover states on the primary "Download PDF Report" button — never used for report chrome, borders, or generic backgrounds.

### Maturity Color Bands (RPRT-03 — single source of truth)

These three colors are the **actual deliverable** of RPRT-03: defined once (in the new `config/dssc-questionnaire.json` `maturity_bands` key per CONTEXT.md D-05) and consumed identically by the server-generated SVG (D-01/D-02) and the priority-list row rendering — never redefined or re-derived in the frontend.

| Band | Score range | Hex | Label (paired text — never color-only) |
|------|-------------|-----|------------------------------------------|
| Red | 1.0–2.0 | `#d64545` | "Needs attention" |
| Orange | 2.0–3.5 | `#e08e2b` | "Developing" |
| Green | 3.5–5.0 | `#399e5a` | "Mature" |

Rule: **color is never the sole signal.** Every band indicator (radar-chart legend entry, priority-list row) pairs the colored dot/segment with both the band label text above and the numeric score (e.g. "3.2 — Developing") — this satisfies color-blind accessibility without adding a new dependency. The green band deliberately reuses the app's existing brand green (`colorSuccess`/`colorLink` in `theme.ts`) — intentional continuity with the "good/compliant" meaning that color already carries throughout the legacy MAMI UI (`StatusChip`'s `yes` state, `CountPill`'s green count), not a new color introduced by this phase.

## UI Considerations

> Populated by the ui-phase UI-consideration probe (Step 9.5) and lifted by plan-phase's
> `## UI Considerations` lift rule via the identical rule as SPEC `## Edge Coverage`. Shape-rooted UI *state*
> coverage (empty / loading / error / populated / partial / overflow / zero-one-many / long-text).
> Empty-state and error-state COPY live in `## Copywriting Contract` above — this section covers
> state coverage and REFERENCES those rows rather than restating the copy (de-dup).

Applicable state considerations resolved: 12 covered, 1 backstop, 0 unresolved. (Dismissed, not listed as rows: `empty`/`partial` for the user's own radar chart and priority list — SCOR-04's completeness gate means a submitted assessment is never partially answered and always produces all 6 dimension scores, so those two states cannot occur for that element.)

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| empty | Admin org-wide radar + per-initiative table | ✅ covered | Zero initiatives with any submitted assessment → org radar is suppressed (not rendered as a zeroed/degenerate hexagon) and the table shows the "No submitted assessments yet" empty state (see Copywriting Contract). |
| loading | Radar chart + priority list (in-app fetch), admin aggregate fetch | ✅ covered | Reuses the existing centered `<Spin size="large" />` pattern already established in `report.tsx`/`admin.heatmap.tsx` while the report/aggregate data is in flight. |
| error | Radar chart + priority list (in-app fetch), admin aggregate fetch | ✅ covered | Reuses the existing `<Alert type="error" showIcon>` + Retry-button pattern (`report.tsx`, `assessments.tsx`) — never a blank page on fetch failure; exact copy in Copywriting Contract. |
| populated | Radar chart (both surfaces) | ✅ covered | Hexagonal 6-axis chart renders via the single server-generated `radar_chart_svg` string (D-01/D-02) — identical markup in-app and in the PDF, no client-side redraw. |
| populated | Priority list | ✅ covered | Always exactly 6 rows (D-06), sorted lowest-to-highest maturity, each row showing dimension name, score to 2 decimal places, and the paired color-band dot + label. |
| partial | Admin per-initiative table | ✅ covered | Rows for initiatives with a submitted assessment show real dimension scores; rows for initiatives with zero submitted assessments show the "No data yet" badge (D-08) inline in the same table — never split into two separate lists. |
| zero-one-many | Priority list | ✅ covered | Always exactly 6 rows (one per config dimension) — count never varies, so no singular/plural copy variance is needed. |
| zero-one-many | Admin per-initiative table | ✅ covered | Summary caption uses correct singular/plural: "1 submitted initiative" vs "N submitted initiatives" (mirrors the existing `total_submitted` pluralization already done in `admin.heatmap.tsx`'s `typeLabel` rendering). |
| long-text | Admin per-initiative table (initiative/org name column) | ✅ covered | Name column uses antd's `ellipsis: true` plus native `title` tooltip on the cell — long organization names truncate visually with a hover tooltip rather than breaking the grid layout. |
| long-text | Report header (initiative name) | ✅ covered | Initiative name wraps rather than truncates in the report page header, consistent with the existing `report.tsx` header treatment (no `text-overflow: ellipsis` there today). |
| overflow | Radar/priority SVG across in-app vs PDF surfaces | ✅ covered | The embedded SVG uses a `viewBox` (not fixed pixel width/height) so it scales correctly in both the responsive in-app card and the fixed-width WeasyPrint PDF page — one markup, two container contexts, per D-02. |
| overflow | Admin per-initiative table row count | ✅ covered | Reuses the existing antd `Table` pagination precedent from `assessments.tsx` (`pagination={{ pageSize: 10, showSizeChanger: false }}`) rather than rendering every initiative unpaginated. |
| overflow | Priority list dimension names | 🧪 backstop | Longest current config name ("Control over Data & Trust", 25 chars) must wrap onto a second line at the declared Body/Label sizes, never truncate — config is user-editable (QSTN-03) so a future edit could produce an even longer name. Enforce via CSS `white-space: normal` / flexible-width layout, not JS truncation. No automated visual-regression test exists yet in this repo (Phase 17 scope) — treat as a held-out visual check at implementation/verification time, not a silent pass. |
