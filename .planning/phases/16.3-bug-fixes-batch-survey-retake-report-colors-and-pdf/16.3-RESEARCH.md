## Summary

All 7 bugs were root-caused by reading the actual implicated source files end-to-end (not just grepping for keywords), and in the case of bugs #1, #3, and #7, cross-checked against this repo's own existing passing test suite to separate "backend is broken" from "backend is fine, frontend never calls it."

**The single most important finding:** bugs #1 and #3 are **not** backend defects. Phase 15 (HIST-01 gap-closure) and Phase 16 (D-04) already built and fully tested the correct multi-assessment machinery — a real `POST /initiatives/{id}/retake` endpoint that unlocks editing and version-bumps, and a real `?assessment_id=` query param on every report endpoint that targets a specific past version. Both are proven correct by `backend/tests/api/test_retake_flow.py` and `backend/tests/api/test_reports.py::test_report_data_specific_assessment_id_returns_that_version`, which pass today. The bugs exist because **two specific frontend call sites never wire up to that already-correct backend**: `TopNav.tsx`'s nav-drawer link to `/questionnaire` is a bare `<Link>` with no retake logic, and `assessments.tsx`'s "View report" table column is a bare `<Link to="/report">` with no `assessment_id` in its search params. Bug #7, by contrast, **is** a real backend defect — `admin.py`'s `list_initiatives()` query counts raw `questionnaire_answer` rows across every assessment (draft + submitted) instead of counting completed (submitted) `Assessment` rows.

**Primary recommendation:** Fix each bug at its one exact, now-identified location. Do not build a "shared assessment resolver" abstraction for #1/#3/#7 — there is no shared code path to fix once; they are three independent, single-file-scoped patches (two frontend wiring fixes, one backend query rewrite + schema/frontend column change).

## Bug #1 — Retake-save fails

**Root cause, file:line evidence:**

1. `frontend/src/components/layout/TopNav.tsx:24-29` — the hamburger-drawer nav item list:
   ```ts
   const navItems: Array<{ label: string; to: '/dashboard' | '/questionnaire' | '/about' | '/admin' }> = [
     { label: 'Dashboard', to: '/dashboard' },
     { label: 'Dataspace Maturity Assessment', to: '/questionnaire' },
     ...
   ```
   Rendered at line ~100 as a bare TanStack Router `<Link to={to}>` with only `onClick={() => setDrawerOpen(false)}` — no status check, no API call.

2. Contrast with `frontend/src/routes/_app/dashboard.tsx:101-130` (`handleStartOrRetake`) — the **only** correct entry point today. When `initiative.status === "submitted"` it opens `Modal.confirm(...)` and, on confirm, calls `await api.post(\`/initiatives/${initiative.id}/retake\`)` **before** `navigate({ to: "/questionnaire" })`.

3. `frontend/src/routes/_app/questionnaire.tsx` (the `/questionnaire` route component) never reads or reacts to `initiative.status` at all — it only fetches config/answers/last-viewed-category and renders `WizardPage`. So navigating there directly after a submission renders a **blank** wizard (no saved answers — confirmed: `GET .../answers` returns `[]` when no draft Assessment exists, `backend/app/api/v1/questionnaire.py:244-245`), which is consistent with the user's own description ("I can start filling the survey").

4. The failure surfaces on save: `backend/app/api/v1/questionnaire.py:158-159`, inside `upsert_answer`:
   ```python
   if initiative.status == InitiativeStatus.submitted:
       raise HTTPException(status_code=403, detail="Submitted assessments cannot be edited")
   ```
   Since the TopNav path never called `/retake`, `Initiative.status` is still `submitted`, so every `PUT /questionnaire/initiatives/{id}/answers/{qid}` 403s.

5. UX mechanism the user actually sees: `frontend/src/hooks/useDebouncedSave.ts`'s `saveWithRetry` catches the 403, retries 3× with backoff (1s/2s/4s — pointless for a 403, since it's not a 429), then sets `SaveState = "failed"`, which `WizardPage.tsx`'s `AutosaveBadge` renders as a red "Save failed" badge with a "Retry save" button that will also just fail again (root cause isn't touched by retrying).

**Fix (HIGH confidence):** The wizard-entry logic that currently only lives in `dashboard.tsx`'s `handleStartOrRetake` must run for **every** entry point into `/questionnaire`, not just the Dashboard CTA. Two complementary approaches:
- **Primary:** extract `handleStartOrRetake`'s logic (fetch `/initiatives/me`, if `status === "submitted"` show the existing `Modal.confirm` and call `POST /initiatives/{id}/retake` before navigating) into a shared helper (e.g. a small hook/module under `frontend/src/lib/` or `frontend/src/hooks/`), and call it from `TopNav.tsx`'s nav item instead of rendering a bare `<Link>` — swap the `<Link to="/questionnaire">` for a clickable element that runs the shared helper then navigates.
- **Defense-in-depth (optional, recommended in addition):** `questionnaire.tsx` already fetches `/initiatives/me` (line 16-23) — it could also guard on `initiative.status === "submitted"` and redirect to `/dashboard` (or trigger the same confirm-then-retake flow) rather than silently rendering a blank, doomed-to-403 wizard. This protects against *any* future or existing entry point that bypasses the confirm flow (bookmarks, back-button, etc.).

**Do NOT:** auto-call `/retake` silently on `/questionnaire` mount without the confirmation dialog — `retake_initiative`'s own docstring and this repo's Key Decisions record **D-13** as a deliberate design constraint: "a retake is an explicit action on a completed assessment, never an implicit side effect." Silently retaking on mount would destroy this guarantee (the modal explicitly warns "you'll answer all 52 questions again from scratch — nothing carries over").

**Existing regression coverage to build on:** `backend/tests/api/test_retake_flow.py` (3 tests, all passing) already proves the backend contract end-to-end. No backend change is needed for bug #1 — this is a frontend-only fix. A new frontend test (or Playwright/manual check) should cover: nav-drawer "Dataspace Maturity Assessment" click on a submitted initiative → confirm modal → `POST /retake` called → lands on a blank, editable wizard → save succeeds (200, not 403).

## Bug #3 — "View Report" always shows/downloads the newest survey

**Root cause, file:line evidence:**
- `frontend/src/routes/_app/assessments.tsx:80-88`, the `versionColumns` "Report" column:
  ```ts
  {
    title: "Report",
    key: "report",
    // Phase 15 scope: links to the existing single /report view (always
    // reflects the current live assessment). A true per-version archived
    // report is Phase 16's job (D-16 explicitly scopes this phase's
    // history view to "boring tabular", not a rebuilt report).
    render: () => <Link to="/report">View report</Link>,
  },
  ```
  The `render` callback receives `(value, record)` but ignores both — every row's link is identical, with **zero** search params. The comment is itself stale: Phase 16 *did* ship the "true per-version" capability the comment says is still pending, but this link was never updated to use it.
- `frontend/src/routes/_app/report.tsx:18-26` (`useReportSearchParams`) already reads `assessment_id` from the URL search params, and `frontend/src/lib/reports.ts:55-63` (`fetchReportData`) already forwards it as `?assessment_id=` to `GET /initiatives/{id}/report/data`. The download button (`report.tsx:149-179`, `handleDownload`) also already appends `assessment_id` to the PDF URL when present (line 158).
- Backend: `backend/app/services/dimension_scoring.py:85-119` (`resolve_report_assessment`) is the single resolver every report/PDF/mail endpoint uses (`backend/app/api/v1/reports.py`, all 5 routes). With `assessment_id=None` it defaults to the highest-version **submitted** assessment (D-04 default = "current report") — this is exactly why, with no param, every click on every history row lands on the newest survey regardless of which row was clicked.

**Proof the backend path is correct today:** `backend/tests/api/test_reports.py::test_report_data_specific_assessment_id_returns_that_version` (passing) and `::test_report_data_foreign_assessment_id_returns_404_idor` (ownership-safe 404, not leaking cross-initiative data).

**Fix (HIGH confidence):** In `assessments.tsx`, change the column render to use the row record and pass `assessment_id` as a TanStack Router `search` param:
```ts
render: (_: string, record: AssessmentSummary) => (
  <Link to="/report" search={{ assessment_id: record.id }}>View report</Link>
),
```
No `validateSearch` is registered on the `/_app/report` route (confirmed by reading `report.tsx`'s own comment at lines 12-16, which explicitly documents this as intentional — "loosely typed search, cast at the read site... so an arbitrary extra query param never breaks navigation"), so this is a safe, additive change with no route-config changes needed. The PDF-download button's own `assessment_id` forwarding (already correct, `report.tsx:158`) will then work automatically once the user lands on `/report?assessment_id=N` from the right link — no separate fix needed for "the PDF download is also of the newest survey," since that symptom is downstream of the same missing link param, not an independent bug in the download code path.

## Bug #5a — PDF score status dot is clipped

**Root cause hypothesis (MEDIUM confidence — pattern-matched to a documented, already-fixed bug class in this exact file, not visually re-confirmed locally):**

The band-color dot that sits immediately next to a score only appears in one place matching "next to the actual score (1.00–5.00)": the per-question rows in the **Submitted answers** card, `backend/app/templates/report.html:220-232`:
```html
<div class="answers-row" style="display: flex; gap: 16px; padding: 12px 0; border-bottom: 1px solid #f0f0f0; align-items: flex-start;">
  <div style="flex: 1; min-width: 0;">
    ...
  </div>
  <div style="display: flex; align-items: center; gap: 8px; white-space: nowrap;">
    <span style="display: inline-block; width: 10px; height: 10px; border-radius: 50%; background: {{ answer.band_color }};"></span>
    <span style="font-size: 14px; font-weight: 600; color: #008ecf;">{{ "%.2f"|format(answer.score) }}</span>
  </div>
</div>
```
This is a **nested flex container**: `.answers-row` is `display: flex`, and its second child — the dot+score wrapper — is *itself* `display: flex`, with no `flex-shrink: 0` reserved on either the wrapper or the dot span. This is precisely the anti-pattern this same file's CSS comments already document and fixed once before, for a different block:

> `.priority-row` comment, `report.html:70-76`: *"Single-level flex only... a nested flex-inside-flex here previously triggered WeasyPrint 69.0 bugs in justify-content free-space distribution and intrinsic-width calculation, breaking the score column alignment in the PDF only."*

That fix (Phase 16-05 gap-closure, `STATE.md` Key Decisions) flattened `.priority-row`/`.legend` to a single flex level with a fixed-width, non-shrinking score column, specifically to work around WeasyPrint 69.0. The "Submitted answers" section, however, was added **later**, in Phase 16.1 (RPRT-05 — see `REQUIREMENTS.md` line 31: "added Phase 16.1 (INSERTED)"), i.e. *after* the 16-05 gap-closure had already landed and closed out Phase 16. It never received the same flattening treatment, and reintroduces the exact nested-flex shape that class of WeasyPrint bug targets — the band-dot (a `width:10px; height:10px` circle) is the element most likely to be visibly squeezed down to "a small hint... doesn't fully show" if the inner flex wrapper's available width gets miscalculated by WeasyPrint under space pressure (long question text in the sibling `flex:1` column is exactly the kind of space pressure that triggers it).

**Fix (apply the identical, already-proven pattern from `.priority-row`):** Flatten the nested flex — make the dot and score direct children of `.answers-row` itself (removing the inner wrapper `div`), and give the dot `flex-shrink: 0` explicitly:
```html
<div class="answers-row" style="display: flex; align-items: center; gap: 8px; padding: 12px 0; border-bottom: 1px solid #f0f0f0;">
  <div style="flex: 1; min-width: 0;">
    ...
  </div>
  <span style="display: inline-block; width: 10px; height: 10px; min-width: 10px; border-radius: 50%; background: {{ answer.band_color }}; flex-shrink: 0;"></span>
  <span style="font-size: 14px; font-weight: 600; color: #008ecf; min-width: 48px; text-align: right; white-space: nowrap; flex-shrink: 0;">{{ "%.2f"|format(answer.score) }}</span>
</div>
```
(Adjust `align-items` on `.answers-row` — note the text column uses `align-items: flex-start` today for multi-line question text; keep that on `.answers-row` and let the dot/score wrap in a `align-self: center` if vertical alignment regresses — verify visually.)

**Verification path (per established project practice, see `STATE.md` Phase 16-05):** WeasyPrint's native libs are not available in this local sandbox (a standing, repeatedly-logged limitation across Phases 12-16.2). This fix cannot be visually confirmed locally. Per this repo's own precedent, defer visual confirmation to a real render on the Railway Integration deployment (the same path used to close out the analogous 16-05 gap-closure bugs) — flag this explicitly as a `checkpoint:human-verify` item in the plan, not a self-verifying automated check.

## Bug #6 — Buttons should have square corners (DSSC brand)

**Root cause, file:line evidence:**
- `frontend/src/lib/theme.ts:11,20` — antd `ConfigProvider` theme (`mamiTheme`, wired in `frontend/src/main.tsx:21`): global `token.borderRadius: 8` and `components.Button.borderRadius: 8`. This is the one place a global fix is possible for antd `<Button>` components.
- **However**, a theme-token-only fix is insufficient. Grep across `frontend/src` for `borderRadius` finds **86 occurrences across 20 files**, the overwhelming majority of which are **inline `style={{ borderRadius: "8px" }}` (or similar) set directly on individual `<Button>` (antd) and plain `<button>` elements** at call sites — e.g. `dashboard.tsx` (8 occurrences, including the "Retake"/"Generate Heatmap"/"Register Initiative" buttons), `admin.index.tsx` (7), `report.tsx` (4), `WizardPage.tsx` (10, including the "← Previous"/"Next →"/"Retry save" plain `<button>` elements, which are **not** antd components at all and are entirely untouched by any `ConfigProvider` theme change), plus `register.tsx`, `login.tsx`, `reset-password.tsx`, `forgot-password.tsx`, `initiative.tsx`, `about.tsx`, `index.tsx`, `admin.heatmap.tsx`, `assessments.tsx`. Inline `style` always wins over antd's CSS-variable-driven theme, so these will stay rounded regardless of any `theme.ts` change.

**Live DSSC reference, verified directly (not assumed) by fetching `https://dssc.eu`'s actual compiled stylesheet** (`https://dssc.eu/assets/styles-BEsVqohA.css`, fetched this session):
```css
.btn{font-family:var(--font-display);letter-spacing:.04em;cursor:pointer;white-space:nowrap;
     border:1.5px solid #0000;border-radius:0; ... }
```
Confirmed: DSSC's real button style is exactly `border-radius: 0` (not a small radius, not a design-system approximation — the literal live value). For reference (not in scope per the bug report, which names buttons only): `.card{...border-radius:var(--radius-none);...}` also resolves to `0px` on the live site (`--radius-none: 0px`, defined alongside a full scale `--radius-sm: 4px` / `--radius-md: 8px` / `--radius-lg: 14px` / `--radius-pill: 999px` that DSSC deliberately does *not* use for buttons/cards) — i.e. DSSC's brand deliberately picks 0 for these elements even though rounded options exist in their own token scale. Worth surfacing to the user as a discretionary follow-up, not folding into this locked 7-bug scope.

**Fix (HIGH confidence on the value; the antd-version mechanism is standard antd v6 `ConfigProvider` theming — `frontend/package.json` confirms `"antd": "^6.3.0"`):**
1. `theme.ts`: set `token.borderRadius: 0` and `components.Button.borderRadius: 0` (covers any antd `<Button>` that has no inline override — few, but some exist, e.g. `admin.index.tsx`'s "View Aggregated Heatmap" default-type button has no inline `borderRadius` today per the read above).
2. Audit and change every inline `borderRadius` set on a `<Button>` (antd) or `<button>` (native) element specifically — **not** on `<Card>`/`<div>` boxes (those are out of scope per the bug report's explicit "buttons" wording and the CONTEXT.md's own framing of this as an open discretionary question) — from `"8px"`/`"6px"` to `"0"`/`"0px"`. Grep at plan time with a pattern scoped to button JSX (e.g. search for `<Button` / `<button` occurrences and check the nearest `style={{...borderRadius...}}` in the same JSX element) rather than a blanket find-replace on `borderRadius`, since the same files also style non-button rounded boxes that must stay untouched.

**Confidence note:** the *value* (0) and the *antd mechanism* (ConfigProvider token override) are HIGH confidence, directly verified. The *completeness of the inline-override audit* is necessarily something the planner/executor must grep-and-verify at implementation time — I did not enumerate all 86 occurrences line-by-line here (that belongs in the plan's task breakdown, not this research), but the representative sample above (dashboard.tsx, admin.index.tsx, report.tsx, WizardPage.tsx) confirms the pattern is real and widespread enough that "just change theme.ts" will visibly fail to fix most buttons.

## Bug #7 — Admin panel: completed-assessment count, not raw answer count

**Root cause, file:line evidence:** the user named "the second tab called Dataspace Maturity Assessments" specifically — this is `admin.index.tsx`'s `tabItems[1]` (`key: "questionnaires"`, `label: `Dataspace Maturity Assessments (${initiatives.length})``), which renders `initiativeColumns` (`admin.index.tsx:169-207`) sourced from `GET /admin/initiatives`. The "Answers" column (`{ title: "Answers", dataIndex: "answer_count" }`) maps to `AdminInitiativeRow.answer_count`, computed in `backend/app/api/v1/admin.py`'s `list_initiatives()` (lines 204-239):
```sql
SELECT i.id, i.name, i.participant_type, i.status, i.created_at,
       u.email AS user_email,
       COUNT(qa.id) AS answer_count
FROM initiative i
LEFT JOIN "user" u ON u.id = i.user_id
LEFT JOIN assessment a ON a.initiative_id = i.id
LEFT JOIN questionnaire_answer qa ON qa.assessment_id = a.id
GROUP BY i.id, i.name, i.participant_type, i.status, i.created_at, u.email
ORDER BY i.created_at DESC
```
This counts every `questionnaire_answer` row across **every** `Assessment` (draft AND submitted) ever created for the initiative — no `WHERE a.status = 'submitted'` filter, and no distinction between assessments at all. This exactly matches the user's own diagnostic ("Whenever I see a figure higher than 52, I know they've at least started it a second time") — 52 is one full config's question count (confirmed live: `config/dssc-questionnaire.json`, 8+9+6+9+9+11 = 52 across 6 categories, per Phase 16.2 session notes in `STATE.md`), so >52 today just means "more than one assessment's worth of answer rows exist in total," not anything about completion.

**Desired behavior:** count of *completed* (submitted) assessments per user/initiative, plus an indicator if a draft (in-progress) next assessment exists.

**Fix (HIGH confidence on approach; exact SQL phrasing is an implementation detail for the plan):**
1. Rewrite `list_initiatives()`'s query to compute two separate aggregates instead of one raw `COUNT(qa.id)`:
   - `completed_assessment_count`: `COUNT(DISTINCT a.id) FILTER (WHERE a.status = 'submitted')` (Postgres `FILTER` clause — this repo already targets Postgres exclusively, `SQLModel`/`sqlalchemy`, so this is idiomatic here) or an equivalent correlated subquery/`CASE WHEN` — avoid a naive `JOIN assessment + JOIN questionnaire_answer + GROUP BY` producing a Cartesian-product miscount when both a submitted and a draft assessment exist simultaneously for the same initiative (a real, common case per this bug report's "in-progress next one" scenario) — worth a fresh single-purpose query per initiative or a validated aggregate rather than extending the existing multi-join in place.
   - `has_draft_in_progress: bool` — `EXISTS (SELECT 1 FROM assessment WHERE initiative_id = i.id AND status = 'draft')`.
2. `AdminInitiativeRow` (Pydantic model, `admin.py:84-91`): replace `answer_count: int` with `completed_assessment_count: int` and add `has_draft_in_progress: bool`.
3. Frontend `admin.index.tsx`: update the `AdminInitiativeRow` interface (lines 25-33) to match, rename the "Answers" column to something like "Completed Assessments" (`dataIndex: "completed_assessment_count"`), and add a new column (e.g. an antd `Tag`/icon rendering only when `has_draft_in_progress` is true — "In progress" badge) — matching the existing `Tag`-based status-rendering idiom already used two columns over (`{ title: "Status", ... render: (v) => <Tag color={...}>{v}</Tag> }`, line 178-183).

**Existing test to update, not just add to:** `backend/tests/api/test_admin.py::test_list_initiatives_returns_user_email_and_answer_count` (line 112) currently asserts the *old, buggy* shape (`row_a["answer_count"] == 3`) — this test's assertions must change to match the new field names/semantics as part of this fix, not be left green-but-wrong.

**Scope boundary respected:** the bug report names only the "Dataspace Maturity Assessments" tab. The separate **Users** tab (`admin.index.tsx`'s `usersExpandable` row, "Answers saved" field, sourced from a *different* endpoint/query — `list_users()`, `admin.py:140-184`, which has the identical raw-count pattern) is not named in the bug report. Flag as a discretionary consistency question for the user/planner (fix both for consistency vs. fix only what was reported) rather than silently expanding scope.

## Architecture Patterns

### Pattern: Assessment resolution already has a correct, tested single source of truth — reuse it, don't reinvent it
`backend/app/services/dimension_scoring.py` already draws a careful, documented distinction between three assessment-lookup functions, each with a narrow, non-overlapping purpose:
- `get_current_assessment` — most-recent **draft** only (what am I filling in right now)
- `list_submitted_assessments` — all **submitted**, version-ordered (history list)
- `resolve_report_assessment` — submitted-scoped, optionally targeted by `assessment_id`, defaults to latest (report reads)

Each function's docstring explicitly warns against reusing it for another function's purpose (see `resolve_report_assessment`'s docstring: "This function must never be generalized to draft assessments"). This phase's fixes must respect that boundary — e.g. bug #1's fix must call the existing `POST /retake` endpoint (which itself reuses `_get_or_create_draft_assessment`), not invent a new draft-creation path.

### Pattern: `admin.py`'s existing raw-SQL idiom for list endpoints
`list_users()` and `list_initiatives()` both use `session.execute(text("""..."""))` rather than the SQLModel/SQLAlchemy query builder, with an explicit comment explaining why ("avoid enum deserialization errors on legacy data"). Bug #7's fix should extend this same raw-SQL pattern, not switch to the ORM builder for just this one query — consistency with the surrounding file matters more than which style is "more idiomatic SQLAlchemy" in the abstract.

### Anti-Patterns to Avoid
- **Building a "shared assessment consumer" abstraction for bugs #1/#3/#7:** see Shared Root Cause Analysis above — there is no shared bug to fix once. Three independent patches.
- **Silent auto-retake:** bug #1's fix must preserve the explicit-confirmation UX (`Modal.confirm`) already established for the one correct entry point — do not bypass it for the sake of a "simpler" universal fix.
- **Blanket `borderRadius` find-and-replace:** bug #6's fix must be scoped to button elements only; the same files contain non-button rounded boxes (`Card`, alert banners, badges/pills) that are explicitly out of scope per the bug report's wording.
- **Nested flex containers in WeasyPrint-rendered HTML:** bug #5a is the second occurrence of this exact bug class in `report.html` (first was `.priority-row`/`.legend`, fixed in Phase 16-05). Any *future* WeasyPrint template addition in this file should default to single-level flex with explicit `flex-shrink: 0` / fixed widths on non-growing children, per the pattern already proven in the `.priority-row` fix.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---|---|---|---|
| "Which assessment does this request mean?" | A new resolver function, a new query, a new endpoint | `resolve_report_assessment` (reports), `get_current_assessment`/`_get_or_create_draft_assessment` (drafts/answers), `list_submitted_assessments` (history) — all already exist, all already tested | Re-deriving this logic anywhere new risks reintroducing exactly the bug class this phase is fixing (a consumer that doesn't correctly account for multiple assessments) |
| Retake state transition | A second "start new assessment" code path triggered from TopNav | `POST /initiatives/{id}/retake` (already exists, already tested, already the one correct call site in `dashboard.tsx`) | Two independent implementations of "reset status + version-bump" would drift; call the existing endpoint from the new call site instead |
| Square-corner button styling | Per-component CSS overrides invented ad hoc, or a new CSS file | antd v6 `ConfigProvider` `theme.token.borderRadius` / `theme.components.Button.borderRadius` (already the mechanism `theme.ts` uses for every other design token) — plus fixing the inline overrides that currently defeat it | Consistency with the existing theming mechanism; a parallel CSS override system would fight the antd theme rather than complement it |

**Key insight:** almost every "don't hand-roll" risk in this phase is really "don't re-solve a problem this codebase already solved correctly once — find the one place it wasn't wired up, and wire it up."

## Common Pitfalls

### Pitfall 1: Assuming the bug is where the data is displayed, not where it's requested
Bug #3 looks like a "report page" bug, but the report page (`report.tsx`) already renders correctly *given* an `assessment_id`. The bug is entirely upstream, in the link that never supplies one. When fixing, verify the fix at the request-construction site, not by touching `report.tsx`.

### Pitfall 2: Confusing "backend accepts optional identity" with "backend defaults are still correct"
`resolve_report_assessment(assessment_id=None)` deliberately defaults to "latest submitted" — that's correct, expected behavior for the no-param case (e.g. Dashboard's "Generate Heatmap" button, which intentionally wants the current/latest report). Don't change this default while fixing bug #3 — only fix the caller that should have supplied a specific id but didn't.

### Pitfall 3: WeasyPrint nested-flex intrinsic-width bugs are not visually obvious from reading CSS alone
This repo has already hit this exact bug class once (`.priority-row`, Phase 16-05) and the fix required a real rendered PDF to confirm (human-verify checkpoint against a Railway deployment — local WeasyPrint is unavailable). Bug #5a's fix should be planned with the same expectation: implement the CSS fix, but gate phase completion on a real-render check, not a code-level "looks right" sign-off.

### Pitfall 4: antd theme tokens don't override inline `style` props
`style={{ borderRadius: "8px" }}` on a `<Button>` always wins over `ConfigProvider`'s `components.Button.borderRadius`, because inline styles have higher CSS specificity than antd's CSS-variable-driven class styles. Bug #6 will appear "not fixed" after a `theme.ts`-only change even though the change itself is correct — the remaining rounded corners come from the ~80+ inline overrides, not from the theme being wrong.

### Pitfall 5: Native `<button>` elements are invisible to antd theming entirely
`WizardPage.tsx`'s Previous/Next/Retry-save controls are plain HTML `<button>` elements, not antd `<Button>` — no antd theme change reaches them at all, inline or otherwise. These need direct inline-style edits regardless of what `theme.ts` does.
