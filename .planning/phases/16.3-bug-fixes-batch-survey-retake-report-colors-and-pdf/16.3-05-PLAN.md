<objective>
Fix Bug #7 (admin panel shows raw answer count instead of completed-assessment count) — per CONTEXT.md's locked decision D-02, fix BOTH the "Dataspace Maturity Assessments" tab (the one named in the bug report) AND the "Users" tab (which has the identical defect via a separate endpoint/query, not named in the report but confirmed by research to share the same bug class).

Root cause: `backend/app/api/v1/admin.py`'s `list_initiatives()` computes `COUNT(qa.id)` by joining `questionnaire_answer` through `assessment`, counting every answer row across every assessment (draft AND submitted) ever created for an initiative — no filter on assessment status. `list_users()` has the identical pattern in its per-row query. Since a full assessment has 52 answers, any count > 52 today just means "more than one assessment's worth of rows exist," not anything about completion — matching the user's own diagnostic in the bug report.

Purpose: replace the raw answer count with `completed_assessment_count` (submitted `Assessment` rows only) and add `has_draft_in_progress` (a boolean, not a count) on both endpoints, using a `FILTER`/`EXISTS` approach — not a naive multi-join `GROUP BY` — to avoid a Cartesian-product miscount when an initiative has both submitted and draft assessments simultaneously (a real, common case this bug report explicitly anticipates: "a symbol that they're underway with a next one").
Output: rewritten `list_initiatives()`/`list_users()` SQL + Pydantic models, an updated existing test (not left green-but-wrong), and updated frontend columns on both Admin Panel tabs.
</objective>

**`list_initiatives()` (lines 204-239):** replace the query and row-building loop. Use `COUNT(DISTINCT a.id) FILTER (WHERE a.status = 'submitted')` (not a join through `questionnaire_answer` — counting `Assessment` rows directly, not answer rows, sidesteps the Cartesian-product risk entirely) plus a correlated `EXISTS` for the draft indicator:
```python
result = session.execute(
    text("""
    SELECT i.id, i.name, i.participant_type, i.status, i.created_at,
           u.email AS user_email,
           COUNT(DISTINCT a.id) FILTER (WHERE a.status = 'submitted') AS completed_assessment_count,
           EXISTS (
               SELECT 1 FROM assessment a2
               WHERE a2.initiative_id = i.id AND a2.status = 'draft'
           ) AS has_draft_in_progress
    FROM initiative i
    LEFT JOIN "user" u ON u.id = i.user_id
    LEFT JOIN assessment a ON a.initiative_id = i.id
    GROUP BY i.id, i.name, i.participant_type, i.status, i.created_at, u.email
    ORDER BY i.created_at DESC
""")
)
rows = []
for row in result.mappings():
    rows.append(
        AdminInitiativeRow(
            id=row["id"],
            user_email=row["user_email"] or "unknown",
            name=row["name"],
            participant_type=row["participant_type"],
            status=row["status"],
            created_at=row["created_at"].isoformat(),
            completed_assessment_count=row["completed_assessment_count"] or 0,
            has_draft_in_progress=bool(row["has_draft_in_progress"]),
        )
    )
return rows
```

if initiative_id:
    stats_result = session.execute(

            SELECT
                COUNT(DISTINCT a.id) FILTER (WHERE a.status = 'submitted') AS completed_assessment_count,
                EXISTS (
