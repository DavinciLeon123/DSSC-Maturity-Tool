# Phase 16.3 Plan 05: Admin Panel Completed-Assessment Count Summary

**Replaced admin.py's raw `questionnaire_answer` row COUNT with a `completed_assessment_count`/`has_draft_in_progress` pair computed via `COUNT(DISTINCT) FILTER`/`EXISTS` on both `list_initiatives()` and `list_users()`, plus matching frontend columns/indicators on both Admin Panel tabs.**

## Accomplishments
- `list_initiatives()`/`list_users()` in `backend/app/api/v1/admin.py` now compute `completed_assessment_count` (submitted `Assessment` rows only, via `COUNT(DISTINCT a.id) FILTER (WHERE a.status = 'submitted')`) and `has_draft_in_progress` (correlated `EXISTS`), replacing the old `COUNT(qa.id)` that summed answer rows across every draft+submitted assessment ever created for an initiative
- Rewrote both existing admin list tests to assert the new field names/semantics, including a simultaneous submitted+draft scenario proving no Cartesian-product miscount (2 completed, `has_draft_in_progress=True`, not an inflated count)
- Updated the Admin Panel frontend: Assessments tab's "Answers" column renamed to "Completed Assessments" plus a new "Next Assessment" `Tag`-based in-progress indicator; Users tab's "Answers saved" field renamed to "Completed assessments" plus a matching "Next assessment" indicator

## Decisions Made
- Counted `Assessment` rows directly rather than answer rows — this is a structurally different (and correct) query, not just a filtered version of the old one, since `Assessment` is the one-row-per-attempt entity while `questionnaire_answer` is one-row-per-question (52 per full assessment)
- Fixed both Admin Panel tabs (Users and Assessments) in one plan, per CONTEXT.md's locked D-02 decision, since both endpoints shared the identical bug class even though the user's bug report only named one tab
