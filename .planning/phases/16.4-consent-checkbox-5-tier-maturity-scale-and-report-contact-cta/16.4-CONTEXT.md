<decisions>
## Implementation Decisions (locked, resolving 16.4-RESEARCH.md's 4 Open Questions)

### D-01 — Tier 2 spelling: "Preparatory"
The user's original "Prepatory" is a typo. Locked spelling for all 5 tier names: **Exploratory, Preparatory, Implementation, Operational, Scaling** (exactly as originally specified, with this one correction).

### D-02 — 5-tier labels are decoupled from the existing 3-color band system (confirms research's technical finding as the locked approach)
Per `16.4-RESEARCH.md`'s Architecture Patterns §2: `config/dssc-questionnaire.json`'s existing 3-entry `maturity_bands` array (colors, thresholds 1.0-2.0/2.0-3.5/3.5-5.0, RPRT-02/03 locked/shipped) stays **exactly as-is** — colors and their thresholds do not change. A new, independent `maturity_tiers` config array (5 entries, thresholds 1.00-1.49/1.50-2.49/2.50-3.49/3.50-4.49/4.50-5.00 per D-01's spelling) and a sibling `get_maturity_tier()` function are added. Only `PriorityListItem.band_label`'s source switches from `get_maturity_band()` to `get_maturity_tier()` — `band_color`, the radar chart, and per-answer dots are unaffected and keep using the unchanged 3-color system.

### D-03 — PDF legend: add a second, separate 5-tier legend block (does not touch the existing 3-color legend)
The user chose to rework the PDF legend rather than leave it untouched. **Locked design** (not left to executor discretion, since research flagged this needs an actual shape, not just "yes/no"): the existing 3-entry color legend (`report.html:203-210`, dot + color-band label, e.g. red dot + "Needs attention") stays completely unchanged — it correctly explains what the 3 dot colors mean, which is not changing. A **new, separate legend block** is added alongside/near it, listing all 5 maturity tiers as plain text rows (tier name + its score range, e.g. "Exploratory (1.00–1.49)") with **no color dot** — since a single color does not map 1:1 onto 5 tiers, attaching a dot to each tier row would misleadingly imply a false one-to-one color/tier correspondence. This keeps the two systems (coarse 3-color visual banding, fine 5-tier text labeling) visually and semantically distinct rather than conflated. Same 5-tier legend block should be considered for the in-app report page too if/when a legend is added there (research confirmed no legend currently exists in `report.tsx` at all — out of scope to add one there unless the planner judges it necessary for the label to make sense without the PDF's legend).

### D-04 — Report-page CTA (Requirement 3): in-app only, not duplicated into the PDF
Confirms research's recommendation. The PDF's existing "Get expert help" box (`report.html:240-250`, Phase 16.1/16.3) stays untouched with its current wording. The new thank-you + `mailto:info@dssc.eu` CTA is added only to the in-app `/report` page (`frontend/src/routes/_app/report.tsx`).

### D-05 — Consent checkbox copy: draft reasonable placeholder text
No DSSC house copy exists in this repo for this. Draft clear, reasonable placeholder wording (e.g. "I agree that the data I submit in this assessment is collected and stored by DSSC.") and flag it explicitly as placeholder/discretionary in the plan and PR description — easy to swap later if DSSC provides real legal/privacy-notice text.

</decisions>
