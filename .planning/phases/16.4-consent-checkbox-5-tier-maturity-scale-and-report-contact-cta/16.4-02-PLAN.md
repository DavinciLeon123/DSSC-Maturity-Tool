**IMPORTANT — a bug in RESEARCH.md's own example code, do not copy it verbatim:** `16.4-RESEARCH.md`'s "Code Examples" section proposes `get_maturity_tier` using the exact same boundary-scan idiom as `get_maturity_band` (`tier["min"] <= score < tier["max"]`, plus an inclusive-last-tier special case). That idiom is correct for `maturity_bands` because bands are CONTIGUOUS (orange's max 2.0 == green's min 2.0 — the shared-boundary "higher band wins" rule matters). The 5 tiers are NOT contiguous — they have deliberate 0.01 gaps (exploratory max 1.49, preparatory min 1.50). Under the contiguous-style scan, a score of exactly 1.49 (a completely ordinary, valid 2dp-rounded score) would satisfy neither `1.00 <= 1.49 < 1.49` (false — not `<`) nor the next tier's `1.50 <= 1.49` (false) and neither is the last tier — so `get_maturity_tier(1.49, tiers)` would raise `ValueError` for a normal score. **This plan's task below specifies the correct implementation: inclusive on BOTH ends (`tier["min"] <= score <= tier["max"]`), no special last-tier casing needed, since the tiers' deliberate gaps make each 2dp-rounded score match unambiguously.** The new boundary test in Task 3 exists specifically to catch this class of bug — it must pass, including at 1.49/2.49/3.49/4.49 (each tier's own max).
