# Phase 16.4: Consent checkbox, 5-tier maturity scale, and report contact CTA - Research

**Researched:** 2026-08-05
**Domain:** In-repo implementation research (FastAPI/SQLModel/PostgreSQL backend + React/TanStack Router/antd v6 frontend) — no new libraries, no external ecosystem research needed. This document maps each of the 3 requirements to exact current code (file:line) and the precise change required.
**Confidence:** HIGH — every claim below is grounded in a direct file read, not a grep guess. No Context7/WebSearch was needed; this is a "read the actual codebase" research task, not a library-selection task.

## Summary

All 3 requirements are small, surgical changes to an already-mature codebase (Phase 16/16.1/16.2/16.3 shipped and are stable). None require a new library, a new architectural layer, or touching the scoring math (Phase 14, correctly out of scope).

1. **Consent checkbox** is a straightforward "add a required boolean column" change. The repo has an even better precedent for this than the one CONTEXT.md pointed at: `add_user_participant_type.py` (revision `e5f6a7b8c9d0`) adds a `NOT NULL` column with a `server_default` in a **single** migration step — no nullable-then-backfill-then-reinstate dance needed, because a `server_default` on `ADD COLUMN` backfills existing rows atomically. (Phase 13's `i9d7e6f5a4b3` nullable-relax migration, which CONTEXT.md cited, actually does the *opposite* — it *relaxes* a NOT NULL constraint to nullable — and is the wrong analog here.)
2. **5-tier maturity scale is the single most important finding of this research**: the existing 3-tier labels ("Needs Attention"/"Developing"/"Mature") and the 3-color red/orange/green banding (RPRT-02/03, locked, shipped) are **the same object** today — one `maturity_bands` config array, one `get_maturity_band()` function, both label and color read off the same band entry. The user's 5 new tiers use different boundaries (1.5/2.5/3.5/4.5) than the existing color boundaries (2.0/3.5), so they **cannot** be the same array without either breaking RPRT-02's locked color thresholds or producing a 5-color chart the user never asked for. The correct fix is to **decouple**: keep the existing 3-entry `maturity_bands` (colors, thresholds, `get_maturity_band`) exactly as shipped, and add a **second, independent** 5-entry tier lookup that only supplies the text label. This is answered definitively below, not left open.
3. **Report CTA** is a pure frontend addition to `frontend/src/routes/_app/report.tsx`, styled to match the page's existing plain-div/inline-style/antd-Button idiom (no `Card` component is used anywhere on this page). The PDF already has an equivalent-purpose "Get expert help" box (`backend/app/templates/report.html:240-250`, Phase 16.1/16.3); the user's own wording ("when a user... sees his scoring") describes the live in-app view specifically, so the minimal-scope reading is: add the new CTA in-app only, leave the PDF's existing box untouched.

**Primary recommendation:** Implement all 3 as small, independent, additive changes; do not introduce any new abstraction layer. For requirement 2, add a new `maturity_tiers` config array + a new `get_maturity_tier()` function (sibling to, not a replacement for, `get_maturity_band()`), and change only the *source* of `PriorityListItem.band_label` / `.priority-band-label` text — nothing else in the report contract shape changes.

## Architecture Patterns

### §1 — Consent checkbox (Requirement 1)

**Current state, traced file-by-file:**

- `backend/app/models/user.py:6-20` — the `User` SQLModel table. No consent field exists. All fields use plain Python-level `Field(default=...)` — **no field in this model uses `sa_column_kwargs`/`server_default` at the model level**; DB-level `server_default` values live only in the Alembic migrations, decoupled from the Python default. This is a real, consistent repo convention (verified across every model file), not incidental.
- `backend/app/schemas/auth.py:19-31` — `UserCreate(BaseModel)` has `email`, `password` (with a `field_validator` that raises `ValueError` → FastAPI auto-converts to 422), and `participant_type: Literal["DSI","SP"] = "DSI"`. No consent field.
- `backend/app/api/v1/auth.py:33-56` — the `/auth/register` handler. Constructs `User(email=..., hashed_password=..., participant_type=user_in.participant_type)` directly (line 41-45), then commits. This is the **only** production write path for new users.
- `frontend/src/routes/_auth/register.tsx` — plain React (no react-hook-form), controlled `useState` per field, POSTs a raw `fetch` (not the shared `api` axios client) to `/auth/register` with `JSON.stringify({ email, password, participant_type: participantType })` (line 27-34). No consent UI exists. Submit is an antd `Button` (`htmlType="submit"`, `loading={loading}`), gated only by native browser `required` on the `Input`/`Input.Password` fields (lines 61-77) — there is **no** existing pattern of disabling submit based on a boolean flag in this file to copy; this phase introduces the first one.
- **No DSSC consent copy exists anywhere in this repo** — confirmed via grep across `frontend/src`, `config/`, and `Briefing.md`. The only "consent" hits are unrelated: `config/dssc-questionnaire.json:565` (a questionnaire *question* about "consent management policies" — a dataspace capability, not registration consent) and `Briefing.md:17/29` (an old MVP note about URL-crawling consent, a removed/out-of-scope subsystem per `MIGR-02`). **The checkbox label wording is Claude's discretion / needs a locked decision — there is no existing house copy to match**, unlike the DSSC-brand color/logo/font work in Phase 16.1/16.2 which had `dssc.eu` to copy from.

**Precedent for the migration — corrected from CONTEXT.md's pointer:**

CONTEXT.md suggested Phase 13's `i9d7e6f5a4b3` nullable-then-backfill pattern as the precedent. Having read it (`backend/alembic/versions/i9d7e6f5a4b3_questionnaire_v2_schema_migration.py:169-174`), **that migration does the opposite of what's needed here**: it *relaxes* `participant_type` from `NOT NULL` to nullable, specifically to let legacy rows the migration itself tags `NULL` remain valid. Requirement 1 needs the reverse shape: a *new* column that must be `NOT NULL` going forward, with existing rows backfilled to a concrete value.

The actually-correct, simpler, already-proven precedent is `backend/alembic/versions/add_user_participant_type.py` (revision `e5f6a7b8c9d0`, `down_revision = "f6a4b3c2d1e9"`):

```python
def upgrade() -> None:
    op.add_column(
        "user", sa.Column("participant_type", sa.String(), nullable=False, server_default="DSI")
    )

def downgrade() -> None:
    op.drop_column("user", "participant_type")
```

This is a **single-step** `ADD COLUMN ... NOT NULL DEFAULT ...` — Postgres backfills every existing row to the `server_default` atomically as part of the `ALTER TABLE`, no separate `UPDATE` statement and no nullable-relax/reinstate two-step needed. This is the pattern to use for `data_consent`.

**Current Alembic head:** confirmed by walking every `down_revision` in `backend/alembic/versions/` — the chain is linear, ending at `k2b3c4d5e6f7` (`assessment_frozen_dimension_scores`, Phase 15 gap-closure). No revision has `down_revision = "k2b3c4d5e6f7"`, confirming it is the current head. The new migration's `down_revision` must be `"k2b3c4d5e6f7"`.

**Recommended concrete change:**

1. **Migration** (new file, `down_revision = "k2b3c4d5e6f7"`):
   ```python
   op.add_column(
       "user", sa.Column("data_consent", sa.Boolean(), nullable=False, server_default=sa.true())
   )
   ```
   `downgrade()`: `op.drop_column("user", "data_consent")`.

2. **`backend/app/models/user.py`**: add `data_consent: bool = Field(default=True)`. **Recommend Python-level default `True`** (not `False`) — this is a deliberate, load-bearing choice: it means the 3 other direct `User(...)` ORM-construction call sites in this codebase (`backend/tests/factories.py:38` `make_user()`, `backend/tests/conftest.py:127` `_create_authed_user()`, `backend/scripts/create_admin.py:24` `create_admin()`) all continue to work **unmodified** and produce consented users, satisfying "every test user has ticked that box" without editing every call site. The real enforcement gate is not this model default — it's the schema validator in step 3.
3. **`backend/app/schemas/auth.py`**: add `data_consent: bool` to `UserCreate` (no default — must be explicitly supplied), with a `field_validator` mirroring `validate_password`'s pattern exactly:
   ```python
   @field_validator("data_consent")
   @classmethod
   def validate_data_consent(cls, v: bool) -> bool:
       if not v:
           raise ValueError("You must agree to data collection to register")
       return v
   ```
   This is the actual server-side gate ("never trust client-only validation") — a request with `data_consent: false` gets a 422, matching the existing password-validator's error shape/precedent exactly.
4. **`backend/app/api/v1/auth.py:41-45`**: add `data_consent=user_in.data_consent` to the `User(...)` construction in `register()`.
5. **`frontend/src/routes/_auth/register.tsx`**: add a `dataConsent` boolean `useState`, an antd `<Checkbox>` (first use in this repo) above the submit button, include `data_consent: dataConsent` in the POST body, and gate submission by disabling the submit `Button` when unchecked (`disabled={!dataConsent || loading}`) — this repo has no existing "disable submit until a condition" pattern in this file to copy verbatim, but it's a standard controlled-component idiom consistent with the file's existing `useState`-per-field style.
6. Optional/discretionary: expose `data_consent` on `UserRead` (`backend/app/schemas/auth.py:34-39`) for transparency — not required by the user's ask, flag as a nice-to-have only.

**Test call sites that will need attention** (found via `User(` grep across `backend/`):
- `backend/tests/factories.py:38` `make_user()` — no change needed if model default is `True` (recommended above).
- `backend/tests/conftest.py:127` `_create_authed_user()` — same, no change needed.
- `backend/scripts/create_admin.py:24` `create_admin()` — same, no change needed.
- `backend/tests/api/test_auth.py:24-55` — `test_register_returns_201_with_user_read_shape` and `test_register_duplicate_email_returns_409` currently POST without `data_consent` in the JSON body. Once the field is required (no Pydantic default on `UserCreate`), these **will** need `"data_consent": True` added to their request payloads, or they'll 422. **A new test should also be added** for the reject-on-false case, mirroring the existing password-validator test pattern in this same file.

### §2 — 5-tier maturity scale (Requirement 2) — THE decisive finding

**The color-band system and the 3-tier text labels are the same object today.** This is not two systems that might ripple into each other — it is **one** system, confirmed by reading every call site:

- `config/dssc-questionnaire.json:722-725`:
  ```json
  "maturity_bands": [
    { "id": "red", "label": "Needs attention", "min": 1.0, "max": 2.0, "color": "#d64545" },
    { "id": "orange", "label": "Developing", "min": 2.0, "max": 3.5, "color": "#e08e2b" },
    { "id": "green", "label": "Mature", "min": 3.5, "max": 5.0, "color": "#399e5a" }
  ]
  ```
  **Do not confuse this with `config/dssc-questionnaire.json:14`** — that's an unrelated per-question answer-option label ("Developing", score 3) inside `default_options`, a completely different config array driving individual question answer wording, not aggregate-score banding. Coincidental shared word only.
- `backend/app/services/report_generator.py:86-103` `get_maturity_band(score, bands)` — explicitly documented as **"the SOLE band-classification function in this codebase... no second inequality chain may exist anywhere else, on any surface"** (RPRT-03). It returns the *whole* band dict (`id`, `label`, `min`, `max`, `color`) for a score. Every consumer below calls this one function.
- `build_priority_list()` (`report_generator.py:106-128`) sets `band_label = band["label"]` **and** `band_color = band["color"]` **from the same `get_maturity_band()` call** — line 123-125.
- `generate_radar_svg()` (`report_generator.py:217-325`) calls `get_maturity_band(overall_average, bands)` only for `band["color"]` (polygon fill/stroke) — label unused here.
- `build_answers_by_category()` (`report_generator.py:131-214`) calls `get_maturity_band(answer_row.score, bands)` only for `band["color"]` (per-answer dot) — label unused here either.
- `backend/app/schemas/report.py:18-32` — `MaturityBand`/`PriorityListItem` Pydantic schemas mirror this exact shape (`id`,`label`,`min`,`max`,`color` / `band_id`,`band_label`,`band_color`).
- `frontend/src/lib/reports.ts:9-30` — `MaturityBand`/`PriorityListItem` TypeScript interfaces mirror the backend exactly, with an explicit comment: "no client-side re-derivation of maturity band color/label from a raw score anywhere downstream of this fetch (RESEARCH anti-pattern, RPRT-03 prohibition)" — **this constraint must be respected**: any plan must keep label derivation server-side, in config, not add client-side score→label logic.

**Why the 5 new tiers cannot simply replace the 3-band array:** RPRT-02 (shipped, complete requirement) locks the color thresholds at exactly 1.0-2.0 (red) / 2.0-3.5 (orange) / 3.5-5.0 (green). The user's 5 new tier boundaries are 1.00-1.49 / 1.50-2.49 / 2.50-3.49 / 3.50-4.49 / 4.50-5.00 (i.e., breakpoints at 1.5/2.5/3.5/4.5) — a **different partition** of the same 1.0-5.0 range. A single score can fall in different-colored bands vs. different-labeled tiers simultaneously (e.g. 2.2 is "orange" by color but "Preparatory" by tier, since orange starts at 2.0 but Preparatory runs 1.50-2.49). There is no way to make one 5-entry array serve both purposes without either (a) silently expanding the shipped 3-color system to 5 colors — an unrequested, undocumented change to a locked requirement — or (b) breaking the boundary alignment. The user's own language ("The final scoring now shows as...") describes displayed **text**, never mentions colors/dots.

**Definitive recommendation: decouple.** Two independent, additive changes:

1. **Add a new config array**, e.g. `config/dssc-questionnaire.json`'s top-level `maturity_tiers` (5 entries, no `color` field needed — it's a pure label lookup):
   ```json
   "maturity_tiers": [
     { "id": "exploratory", "label": "Exploratory", "min": 1.00, "max": 1.49 },
     { "id": "preparatory", "label": "Preparatory", "min": 1.50, "max": 2.49 },
     { "id": "implementation", "label": "Implementation", "min": 2.50, "max": 3.49 },
     { "id": "operational", "label": "Operational", "min": 3.50, "max": 4.49 },
     { "id": "scaling", "label": "Scaling", "min": 4.50, "max": 5.00 }
   ]
   ```
   (Exact spelling of "Preparatory" pending user confirmation per the flagged typo above.) Confirmed safe to add: `backend/app/services/mami_config.py:26-50`'s `load_dssc_questionnaire_config()` only validates zero-question categories — it does not enumerate or require specific top-level keys, so a new key is a pure additive change with zero loader-validation risk. Confirmed via `backend/tests/services/test_dssc_config.py:64-84`'s `bad_config` fixture, which also omits any `maturity_tiers`-equivalent requirement.

2. **Add a new function**, `get_maturity_tier(score, tiers)` in `report_generator.py`, structurally identical to `get_maturity_band()` (same ascending-order scan, same inclusive-top-bound edge case at `score == tiers[-1]["max"]`). **Update `get_maturity_band()`'s docstring** — its current claim ("the SOLE band-classification function in this codebase") becomes inaccurate once a second, deliberately-separate function exists for a different concern (text-tier labeling vs. color-banding); the docstring should be narrowed to state it remains the sole *color*-classification function, and RPRT-03's actual invariant (chart and priority-list share one color source) is unaffected.

3. **Change only the source of `band_label`** in `build_priority_list()` (`report_generator.py:106-128`): keep `band_id`/`band_color` sourced from `get_maturity_band()` exactly as today (color system fully unchanged, RPRT-02/03 stay satisfied); change `band_label` to be sourced from `get_maturity_tier(score, tiers)["label"]` instead. `build_priority_list()`'s signature grows a `tiers` parameter. `build_report_contract()` (`report_generator.py:328-372`) must load `config["maturity_tiers"]` and pass it through. **No Pydantic/TypeScript schema shape changes are needed** — `PriorityListItem.band_label` stays a `str` field, only its value's source function changes. This keeps the diff minimal and avoids touching `docs/api/openapi.json` (no schema change → no docs-freshness CI regeneration needed for this part).

### Anti-Patterns to Avoid

- **Client-side score→label/color re-derivation** — explicitly prohibited by existing code comments in `frontend/src/lib/reports.ts:6-7` and `frontend/src/routes/_app/admin.heatmap.tsx:82-85`. Requirement 2's new tier label must be computed server-side, in `report_generator.py`, from config — never in React.
- **Silently merging the 5-tier labels into the existing 3-color `maturity_bands` array** — would silently break RPRT-02's locked color thresholds (see §2 above). Do not do this even though it looks like the "simpler" one-array change.
- **Two-step nullable-then-backfill-then-reinstate-NOT-NULL migration for `data_consent`** — unnecessary complexity for this case. Use the single-step `ADD COLUMN ... NOT NULL DEFAULT` pattern (`add_user_participant_type.py` precedent) instead of the `i9d7e6f5a4b3` nullable-relax pattern CONTEXT.md pointed at (that migration solves a different problem — relaxing an existing constraint for legacy-row compatibility — not adding a new always-required field).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---|---|---|---|
| Registration consent checkbox | Custom `<input type="checkbox">` + manual DOM validation | antd `Checkbox` (already a dependency, unused elsewhere but standard) | Matches this repo's established all-antd-components convention (`Input`, `Button`, `Alert` already used in the same file) |
| mailto CTA button | A custom link-styled-as-button component | antd `Button` with `href="mailto:..."` prop | antd `Button` natively supports `href`/`target`, renders a real `<a>`; no wrapper needed |
| Server-side consent validation | Manual `if not data.get("data_consent"): raise HTTPException(...)` in the route handler | Pydantic `field_validator` on `UserCreate.data_consent`, mirroring the existing `validate_password` validator (`auth.py:24-31`) | Consistent error shape (422, same `detail` structure) as every other registration validation error already in this schema |
| 5-tier score classification | A second inline if/elif chain somewhere in `report.tsx` or duplicated in `report.html` | One new `get_maturity_tier()` function in `report_generator.py`, config-driven, structurally mirroring the existing `get_maturity_band()` | RPRT-03's "single source of truth, no duplicated inequality chains" precedent applies equally to the new tier concept — this repo already paid down this exact class of bug once (Phase 16 built `get_maturity_band` specifically to avoid two divergent color-threshold implementations) |

**Key insight:** every one of these 3 requirements has a near-identical existing pattern already proven in this exact codebase (a `field_validator`, a single-source classification function, a config-driven band array, a plain antd `Button`/`Checkbox`). None require inventing a new pattern — the work is applying the same shape one more time, correctly scoped.

## Common Pitfalls

### Pitfall 1: Treating `add_user_participant_type.py` and `i9d7e6f5a4b3` as interchangeable migration precedents
**What goes wrong:** Using the nullable-then-backfill-then-reinstate-NOT-NULL pattern (3 migration steps) for a simple new required column, when a single `ADD COLUMN NOT NULL DEFAULT` migration does the same job in one step.
**Why it happens:** CONTEXT.md pointed at `i9d7e6f5a4b3` as "this repo's precedent for exactly this kind of...migration" — but that migration solves the opposite problem (relaxing a constraint for legacy compatibility), not adding a new always-required field to a table with existing rows.
**How to avoid:** Use `add_user_participant_type.py` (`e5f6a7b8c9d0`) instead — `nullable=False, server_default=sa.true()` in one `add_column` call.
**Warning signs:** A migration plan with 3+ steps (relax → backfill → reinstate) for what should be a single `ADD COLUMN`.

### Pitfall 2: Expanding the 3-color band system to 5 colors
**What goes wrong:** Naively replacing `maturity_bands`' 3 entries with the user's 5 tier boundaries, which also changes `get_maturity_band()`'s output for the radar chart fill and every band-color dot — silently regressing RPRT-02 (shipped, locked: "red 1.0-2.0, orange 2.0-3.5, green 3.5-5.0") without anyone asking for that.
**Why it happens:** `band_label` and `band_color` are bundled in the same object today, so it's the path of least resistance to just edit the one array.
**How to avoid:** Add a second, independent `maturity_tiers` array + `get_maturity_tier()` function (see §2). Verify `test_maturity_band_boundaries()` and `test_reports.py`'s `len(body["maturity_bands"]) == 3` assertion still pass unmodified — if either needs to change, the color system was touched by mistake.
**Warning signs:** `config/dssc-questionnaire.json`'s `maturity_bands` array growing to 5 entries, or its existing 3 `min`/`max`/`color` values changing.

### Pitfall 3: Missing the required `data_consent` field in existing registration tests
**What goes wrong:** `backend/tests/api/test_auth.py`'s existing `/register` tests (lines 24-55) POST JSON bodies without `data_consent` — once the field is required with no Pydantic default, these will 422 and fail, looking like an unrelated regression.
**Why it happens:** Easy to add the new required field to the schema/model/frontend and forget the 2 existing test bodies that construct the registration payload by hand.
**How to avoid:** Update both existing test payloads to include `"data_consent": True`; add a new test asserting `data_consent: false` → 422 (mirroring the existing common-password-rejection test's shape/pattern in the same file).
**Warning signs:** `test_register_returns_201_with_user_read_shape` / `test_register_duplicate_email_returns_409` failing after the schema change.

### Pitfall 4: Confusing `config/dssc-questionnaire.json:14`'s "Developing" with the maturity-band "Developing" at line 724
**What goes wrong:** Grepping for the literal string `"Developing"` to "find every occurrence of the old 3-tier labels" turns up a false positive at line 14 — an unrelated per-question answer-option label inside `default_options` (score 3 of 5, used as a fallback for questions that don't override their own options).
**Why it happens:** Coincidental word overlap between an aggregate-scoring band label and an individual-question answer-option label.
**How to avoid:** Only touch `maturity_bands` (line 722-725) and now the new `maturity_tiers` array — never `default_options` (line 4-25) or any per-question `options` override.
**Warning signs:** A diff touching `default_options` or any question's own `options` array when the task is "relabel aggregate scoring bands."

### The exact band-classification pattern to mirror (source: `backend/app/services/report_generator.py:86-103`, this repo)
```python
def get_maturity_tier(score: float, tiers: list[dict]) -> dict:
    """Sibling to get_maturity_band — same ascending-order / inclusive-top-bound
    scan, but classifies a score into one of the 5 maturity_tiers (label only,
    no color) rather than one of the 3 color-coded maturity_bands. The two
    functions are deliberately independent; get_maturity_band remains the
    SOLE source of color classification (RPRT-03)."""
    for tier in tiers:
        is_last = tier is tiers[-1]
        if tier["min"] <= score < tier["max"] or (is_last and score == tier["max"]):
            return tier
    raise ValueError(f"score {score} not covered by any maturity_tiers entry")
```
