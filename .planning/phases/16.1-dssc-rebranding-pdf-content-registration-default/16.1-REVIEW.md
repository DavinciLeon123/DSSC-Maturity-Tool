## Summary

This phase's stated deliverable was a full DSSC rebrand (colors, fonts, logo) across the app and the PDF report, plus a PDF "submitted answers" section and a DSI-only registration default. A prior executor's pass was flagged as incomplete/falsely-claimed and closed out by a gap-closure round (plan `16.1-04`), whose own `16.1-VERIFICATION.md` asserts "zero old-hex remaining" and "the white DSSC logo on the header band" as independently re-verified facts.

Both of those specific claims are false on the actual code as submitted, and the same verification's own grep methodology explains why: it grepped for old brand tokens in exact-case hex form (`#3D52D5`, `#399e5a`, …) and for the presence of an `<img>` tag, but never checked case-insensitively or actually exercised the render path. Two files this phase *did* touch (`WizardPage.tsx`, `report.tsx`) still render the literal deprecated brand colors in lowercase-hex/rgb-decimal form, and the newly-added report logo has no working code path to actually resolve on either surface it's rendered on (in-browser HTML and the PDF download). This is the same failure pattern (rebrand claimed done, not actually done) that this phase was created to fix, recurring inside the fix itself.

Secondary findings cover dead code touched during the rebrand pass (`Sidebar.tsx`, never mounted anywhere) and residual/misleading branding artifacts (stale CSS variable name, un-rebranded favicon).

## Critical Issues

### CR-01: Report logo never actually renders — in the browser view or the PDF

**File:** `backend/app/templates/report.html:168`, `backend/app/api/v1/reports.py:121-123,233-238`

**Issue:** The rebrand added `<img src="assets/logo-dssc-white.png" ...>` to `report.html` (commit `8363c84`, "Copy logo to backend templates directory for WeasyPrint resolution"), but that intent was never wired up:

1. **PDF path** (`download_report_pdf` and `_send_report_email`, both reachable — `download_report_pdf` backs the live "Download PDF Report" button in `frontend/src/routes/_app/report.tsx:156`): `WeasyHTML(string=html_content).write_pdf()` is called with no `base_url`. WeasyPrint resolves relative URLs in a `string=`-constructed document against the process's current working directory, not the templates directory — the relative path `assets/logo-dssc-white.png` will not resolve to `backend/app/templates/assets/logo-dssc-white.png` in any deployment. The image silently fails to load (WeasyPrint logs a warning, doesn't raise) and the PDF ships without the logo.
2. **In-browser HTML path** (`GET`/`POST /initiatives/{id}/report`): the response is served from `/api/v1/initiatives/{id}/report`. A relative `src="assets/logo-dssc-white.png"` resolves against that page URL to `/api/v1/initiatives/{id}/assets/logo-dssc-white.png` — there is no `StaticFiles` mount anywhere in `backend/app/main.py` (confirmed: no `from fastapi.staticfiles import StaticFiles` / `app.mount` in the whole backend) or any other route serving that path, so the browser gets a 404 for the image.

No test in `backend/tests/api/test_reports.py` or `backend/tests/services/test_report_generator.py` catches this — every PDF test mocks `weasyprint.HTML` out entirely (`mocker.patch("weasyprint.HTML")`), and no test asserts the `<img>` tag's `src` actually resolves. `16.1-VERIFICATION.md` line 46 certifies this as "✓ VERIFIED" purely because the string `<img src="assets/logo-dssc-white.png" .../>` is present in the template — it never renders the template end-to-end.

**Fix:** Embed the logo as a base64 data URI at render time (works identically for both the PDF and the in-browser view, with zero dependency on `base_url`/static mounts):
```python
# report_generator.py
import base64

_LOGO_PATH = TEMPLATES_DIR / "assets" / "logo-dssc-white.png"

def _logo_data_uri() -> str:
    data = base64.b64encode(_LOGO_PATH.read_bytes()).decode("ascii")
    return f"data:image/png;base64,{data}"
```
and pass `logo_src=_logo_data_uri()` into the template context, replacing `src="assets/logo-dssc-white.png"` with `src="{{ logo_src }}"`. If the relative-file approach is kept instead, both `WeasyHTML(...)` call sites in `reports.py` must pass `base_url=str(TEMPLATES_DIR)` (or equivalent) — but that only fixes the PDF, not the in-browser HTML response, so the data-URI approach is the only fix that covers both consumers with one change.

### CR-02: Deprecated pre-rebrand color `#3d52d5` still rendered on the questionnaire wizard

**File:** `frontend/src/components/questionnaire/WizardPage.tsx:454-455`

**Issue:**
```tsx
background: "rgba(61,82,213,0.16)",
color: "#3d52d5",
```
`rgba(61,82,213,…)` is the decimal-RGB form of `#3D52D5` — one of the exact deprecated tokens `16.1-VERIFICATION.md` (line 42) explicitly lists as eliminated ("the old globals.css tokens #020059/#41A765/#3D52D5"). It renders the "Question X of Y" pill on every single wizard page, in a file this phase's gap-closure round specifically touched (`bdb1fee "fix(16.1-04): fix 6 app-route files — Rubik→Open Sans, old navy→DSSC Blue rgba"` — `WizardPage.tsx` is not one of the 6 files that commit lists, but it was touched separately in `da57821`/`8ed3760`). It was missed because the verification's grep for `#3D52D5` was case-sensitive against the *hex* string only — it never checked the lowercase form actually used here, nor the equivalent decimal-RGB `rgba()` encoding.

**Fix:**
```tsx
background: "rgba(0,142,207,0.16)",   // DSSC Blue #008ecf, matching the rest of the wizard's accent usage
color: "#008ecf",
```

**File:** `frontend/src/components/layout/Sidebar.tsx`

**Issue:** `Sidebar.tsx` exports `Sidebar()`, but no route or layout imports/renders it (`grep -rn "Sidebar" frontend/src` matches only its own declaration). `_app.tsx` uses `TopNav` exclusively for the app shell. This phase's rebrand commits nonetheless spent a diff (`fix(16.1-04)`/earlier `feat(16.1-01)`) recoloring this component's `var(--color-navy)`/`var(--color-green)` usage — effort spent maintaining unreachable code, and a maintenance trap: a future contributor may reasonably assume `Sidebar.tsx` is the live nav (it duplicates `TopNav`'s nav-item list almost exactly, including the same "Dataspace Maturity Assessment" label) and edit it expecting a visible effect.

**Fix:** Either wire `Sidebar` into a layout that actually uses it, or delete the file. If there's a reason to keep it staged for a future desktop-nav variant, add a one-line comment stating that explicitly (mirroring how `logo-coe-dsc.svg` was deliberately left orphaned with a documented reason elsewhere in this phase).

### WR-02: `--color-navy` CSS variable holds DSSC Blue, not navy — stale, misleading name

**File:** `frontend/src/styles/globals.css:4`

**Issue:**
```css
--color-navy: #008ecf;
```
This token is consumed in `Sidebar.tsx:46` and `questionnaire.tsx:151` under the name "navy" but resolves to DSSC Blue. The rebrand correctly updated every *value* under this name but left the identifier itself referring to the old MAMI navy (`#06004f`) brand. This is exactly the kind of mismatch that causes a future "quick color tweak" to touch the wrong token, or a future reviewer to misjudge intent from the name alone.

**Fix:** Rename to `--color-primary` or `--color-blue` (an alias, `--color-blue`, already exists one line below at line 6 pointing to the same value — collapse to one canonical name and update both call sites).

### IN-02: `.map()` returns a keyless `<>` fragment (React key warning)

**File:** `frontend/src/routes/_app/initiative.tsx:250-254`

**Issue:** Pre-existing (not introduced by this phase — only the inline color/font values on lines 251/252 were touched by the rebrand diff), but present in a file this review covers:
```tsx
{[...].map(([label, value]) => (
  <>
    <dt key={`dt-${label}`}>...</dt>
    <dd key={`dd-${label}`}>...</dd>
  </>
))}
```
The `key` props are placed on the `<dt>`/`<dd>` children, but React requires the key on the element `.map()` itself returns — here, the unkeyed `<>` fragment. This produces a "Each child in a list should have a unique key prop" console warning and risks incorrect reconciliation if `label` values ever change order.

**Fix:**
```tsx
{[...].map(([label, value]) => (
  <React.Fragment key={label}>
    <dt>...</dt>
    <dd>...</dd>
  </React.Fragment>
))}
```
