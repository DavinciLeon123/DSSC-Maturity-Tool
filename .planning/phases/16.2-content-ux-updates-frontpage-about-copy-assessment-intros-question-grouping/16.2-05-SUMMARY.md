## Decisions Made
- **QuestionGroup as a component, not a plain function:** the plan's suggested `renderQuestions()` plain helper (taking `onAnswerChange` as an argument) trips `eslint-plugin-react-hooks` v7's new "refs" rule — it flagged `pendingFlushRef.current` access as reachable during render because it couldn't statically prove the passed-through `handleAnswerChange` closure isn't invoked synchronously inside the helper. The original inline `.map` (passing the same handler as a JSX prop directly to `QuestionCard`) never tripped this rule. Restructuring the same grouping algorithm as a `QuestionGroup` React component — so `onAnswerChange` is forwarded via ordinary JSX props rather than a plain-function argument — resolved it with zero behavior change (Rule 3, blocking issue: lint is a required verification gate).
- **Manual verification via jsdom harness, not a live browser:** this environment has no browser tool, no seeded local Postgres/backend, and no Playwright/Cypress E2E setup (only Vitest + Testing Library). Wrote a throwaway `WizardPage.manual-verify.test.tsx` (deleted before the Task 3 commit, not part of this plan's file list) exercising: fresh-draft welcome screen visibility, zero `PATCH last-viewed-category` calls while `showWelcome` is true (the direct proxy for the Pitfall 1 refresh regression — a refresh is just a fresh mount with the same never-persisted `null` `lastViewedCategoryId`), one-way advance past welcome with correct intro/subsection rendering, and resume-skips-welcome for an in-progress draft. All 4 assertions passed. Cross-checked per-dimension `intro`/`subsections` ordering for all 6 real categories directly against `config/dssc-questionnaire.json` (not the test fixture) — confirmed 8/9/6/9/9/11 question counts and subsection names/counts match `16.2-SOURCE-CONTENT.md` §5 exactly.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Restructured the question-grouping helper from a plain function to a component to satisfy eslint-plugin-react-hooks v7's "refs" rule**
- **Found during:** Task 2 (subsection-grouped question rendering)
- **Issue:** The plan's exact suggested code (`function renderQuestions(category, localAnswers, defaultOptions, onAnswerChange) {...}`, called inline as `{renderQuestions(currentCategory, localAnswers, config.default_options, handleAnswerChange)}`) failed `npm run lint` with `react-hooks/refs`: "Cannot access ref value during render," pointing at the `handleAnswerChange` argument. `handleAnswerChange` closes over `pendingFlushRef.current` (a `useRef`), and the lint rule can't statically prove a plain function invoked during render won't call its argument synchronously — even though `renderQuestions` only ever stores it as a prop for `QuestionCard` to call later in an event handler.
- **Fix:** Converted `renderQuestions` into `QuestionGroup`, a genuine React component taking the same four values as props and rendering the same JSX. Forwarding `onAnswerChange` via a component's props is the same idiom the pre-existing (lint-clean) inline `.map` already used for `QuestionCard` directly, and the rule recognizes it as safe.
- **Files modified:** `frontend/src/components/questionnaire/WizardPage.tsx`
- **Verification:** `npm run typecheck` and `npm run lint` both pass cleanly; grouping output/order unchanged (verified via the throwaway jsdom harness).
- **Committed in:** `e3ebfc8` (Task 2 commit)
