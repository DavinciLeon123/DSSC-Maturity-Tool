## Issues Encountered

**Concurrent-execution git-index race (informational, not a bug in this plan's work):** This plan ran in a shared working directory alongside at least one other concurrently-executing plan (16.2-04). Task 1's commit (`f86b1c3`) unexpectedly included a 34-line change to `config/dssc-questionnaire.json` (per-dimension `intro`/`subsections` fields) that this plan never touched, staged, or listed in its file scope. Immediately before that commit, `git status --short` showed that file as unstaged (` M`, not staged); the inclusion only became visible after the commit completed. This is consistent with two `git add`/`git commit` sequences (this executor and the concurrent 16.2-04 executor) briefly overlapping on the same shared `.git/index` file, not any action taken by this plan's execution. No data was lost — the content is real, intentional work from the other plan, just mis-attributed to this commit's message/hash. For Task 2's commit I added an extra verification step (re-running `git diff`/`git status` immediately before staging and committing, confirming line-for-line 1:1 insertion/deletion counts matching a pure string substitution) and it landed clean with exactly the intended 18 files. Also observed and discarded two additional pieces of environment noise before they could pollute a commit: (1) `frontend/package-lock.json` picked up ~78 lines of npm-metadata-only churn (peer-flag/libc-field normalization) from a first-time `npm install` in this environment — reverted via `git checkout --`, no functional dependency change; (2) `frontend/src/routeTree.gen.ts` showed a pure line-ending (LF/CRLF) diff with zero content change after running `npm run build`/`typecheck` — reverted via `git checkout --`, not committed. The same race recurred the other direction during the STATE.md-update phase: this plan's hand-written STATE.md edits (merged on top of 16.2-04's already-present same-session edits) were written to disk via the Edit tool, then swept into the concurrent 16.2-04 executor's own metadata commit (`f5b2ae3`, "docs(16.2-04): complete questionnaire content contract plan") before this plan's own final commit could run — confirmed via `git show --stat f5b2ae3` and a content grep that all of this plan's intended STATE.md additions landed intact and uncorrupted; this plan's own final metadata commit (`f441bc9`) therefore only contains `ROADMAP.md` (a small `2/6`-count fix) and this `SUMMARY.md`, not a redundant STATE.md diff. Flagging this per this plan's explicit instruction to report git anomalies rather than silently working around them: **future plans/orchestration in this phase should avoid running multiple plan executors against the same working directory concurrently**, or should serialize `git add`+`git commit` sequences (including the state-update phase, not just task commits) across concurrent executors, to eliminate this race entirely. Also observed two related bugs in `gsd-tools` this run: `state advance-plan`/`state update-progress` both hard-failed against this STATE.md's structure (`Cannot parse Current Plan or Total Plans in Phase from STATE.md`, `Progress field not found in STATE.md`) with no writes (safe no-op); `roadmap update-plan-progress 16.2` reported `{"updated": true, ...}` but the diff it actually wrote checked off the wrong plan (`16.2-04-PLAN.md` instead of `16.2-01-PLAN.md`, the plan this session executed) and shifted/dropped a column (`v2.0` milestone missing) in the new phase-16.2 progress-table row — reverted via `git checkout --` and fixed both STATE.md and ROADMAP.md by hand instead, per this session's standing guidance.
