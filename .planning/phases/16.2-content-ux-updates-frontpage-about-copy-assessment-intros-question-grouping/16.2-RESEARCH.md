## Summary

This phase is pure frontend application code + copy — no new libraries, no backend schema changes, no API contract changes. Every one of the 5 deliverables can be implemented with vanilla React/CSS/antd primitives already in use elsewhere in this codebase. The main risks are not technical-unknowns but **codebase-specific wiring pitfalls** found by reading the actual files: (1) an existing `useEffect` in `WizardPage.tsx` that will silently defeat the welcome-screen "only on fresh start" rule unless explicitly guarded; (2) the About page's background is not owned by `about.tsx` but by the shared `_app.tsx` layout wrapper, so "About page color changes" has a scope decision hiding inside it; (3) the live homepage/About copy has already drifted from both the old MAMI text and the new PDF text (Phase 16.1 partially rebranded some strings with its own wording), so the source table can't be applied via literal string search-and-replace — it must be mapped by semantic slot/position; (4) the "Jost app-wide" decision collides with a repo-wide pattern of ~126 inline `fontFamily: "'Open Sans', sans-serif"` declarations across 20 files that bypass both `globals.css`'s CSS variable and antd's `ThemeConfig` token, meaning a CSS-variable-only change will not visually cascade — it requires a broad, mechanical multi-file replace; (5) the subsection-name→question-range mapping in `16.2-SOURCE-CONTENT.md` is a set of contiguous slices over each category's *existing* question array order, which makes a config-extension approach clean and low-risk (confirmed against `config/dssc-questionnaire.json`'s real per-category counts: 8/9/6/9/9/11 = 52).

**Primary recommendation:** Extend `config/dssc-questionnaire.json` with two new optional fields per category (`intro: string`, `subsections: {name, count}[]`) rather than a frontend lookup table — the config endpoint (`GET /questionnaire/config`) returns a raw untyped `dict` with zero Pydantic validation (`response_model` absent, OpenAPI schema is literally `{}`), so this is a zero-backend-code, zero-OpenAPI-diff, fully additive change that keeps all question-related content in one config-driven source of truth, consistent with this project's existing QSTN-03 philosophy ("no code deploy required to change content").

### Pattern 1: Config-driven subsections + dimension intro (recommended data shape)

**What:** Add two optional fields to each category object in `config/dssc-questionnaire.json`:
```json
{
  "id": "cat-1",
  "name": "Governance",
  "intro": "This section assesses how your data space is organized and managed. The questions focus on governance structures, decision-making, the rulebook, operational processes, participant management, and support mechanisms. Together, these elements demonstrate how effectively the data space can operate, onboard participants, manage change, and ensure long-term sustainability.",
  "subsections": [
    { "name": "Governance Framework Establishment", "count": 4 },
    { "name": "Participation Management", "count": 4 }
  ],
  "questions": [ /* unchanged, 8 questions in this category */ ]
}
```
`count` is the number of *consecutive* questions (starting where the previous subsection left off) the subsection covers — verified to sum exactly to each category's question count for all 6 categories (8, 9, 6, 9, 9, 11 = 52) using the mapping already checked against the live config in `16.2-SOURCE-CONTENT.md` §5. No question needs reordering or a `subsection_id` field — position alone determines grouping.

**Why this is safe (verified, not assumed):**
- `GET /questionnaire/config` (`backend/app/api/v1/questionnaire.py::get_questionnaire_config_endpoint`) has **no** `response_model` — it returns the loaded `dict` as-is. Its `docs/api/openapi.json` entry for this route is literally `"schema": {}` (confirmed by reading the generated file). Adding new keys to the JSON cannot change this endpoint's OpenAPI shape, so the `docs-freshness` CI gate (CLAUDE.md) is unaffected — no regeneration needed for this change.
- Every backend consumer of category dicts accesses only specific known keys (`cat["id"]`, `cat["questions"]`, `cat.get("questions")`) — never asserts an exact/closed key set. Checked: `mami_config.py` (`load_dssc_questionnaire_config`'s zero-question guard), `dimension_scoring.py` (`compute_dimension_scores`/category-count helpers), `report_generator.py` (`for question in category["questions"]`). All are additive-safe.
- Existing backend tests (`backend/tests/services/test_dssc_config.py`, `backend/tests/api/test_questionnaire.py`) assert `len(config["categories"]) == 6`, per-question option shapes, and byte-for-parsed equality with the raw JSON file — none assert a closed category key set, so they stay green.
- `report.html` (the PDF template) accesses only `category.name`/`category.answers` on its own report-generator-built structure (not the raw config) — the new `intro`/`subsections` fields cannot leak into the mailed/downloaded PDF. Confirmed this phase's scope is wizard/homepage/About only — **the PDF report is out of scope** for subsections/intro text (not named in any of the 5 success criteria).

**Frontend type addition:**
```typescript
// frontend/src/lib/questionnaire.ts
export interface Subsection {
  name: string;
  count: number;
}

export interface Category {
  id: string;
  name: string;
  intro?: string;
  subsections?: Subsection[];
  questions: Question[];
}
```
Only `WizardPage.tsx` and `StepPills.tsx` import `Category` (checked via repo-wide grep) — `StepPills.tsx` only reads `.id`/`.name`/`.questions.length`, so adding optional fields is a no-op there under `strict: true` TypeScript.

**Rendering algorithm (WizardPage.tsx, replaces the current flat `.map`):**
```tsx
function renderQuestions(category: Category, /* existing per-question props */) {
  if (!category.subsections?.length) {
    // defensive fallback if a category is ever missing subsections
    return category.questions.map((q) => <QuestionCard key={q.id} question={q} ... />);
  }
  const nodes: React.ReactNode[] = [];
  let idx = 0;
  category.subsections.forEach((sub, subIdx) => {
    nodes.push(<SubsectionLabel key={`sub-${subIdx}`}>{sub.name}</SubsectionLabel>);
    for (let i = 0; i < sub.count; i++) {
      const q = category.questions[idx];
      nodes.push(<QuestionCard key={q.id} question={q} ... />);
      idx++;
    }
  });
  return nodes;
}
```
This changes nothing about `Question X of Y` (still `config.categories[...].questions.length`-derived) or `completedCategoryIds`/`answeredCount` (still keyed by flat `localAnswers[q.id]`) — both loop over `category.questions` directly, untouched by this change, matching the locked decision that subsections are "a purely visual/organizational label layered on top."

### Pattern 2: Welcome screen as gated pre-step (not a new route, not a modal)

**What:** A new boolean piece of state in `WizardPage.tsx`, initialized from the same signal the component already uses to decide where to resume:

```tsx
const [showWelcome, setShowWelcome] = useState(lastViewedCategoryId == null);
```

`lastViewedCategoryId` is fetched via `fetchLastViewedCategory` (`frontend/src/lib/questionnaire.ts`) from `GET /questionnaire/initiatives/{id}/last-viewed-category`, which reads `Assessment.last_viewed_category_id` (`backend/app/models/assessment.py`). **This field lives on the `Assessment` row, not the `Initiative`** — and a retake always creates a brand-new `Assessment` row via `_get_or_create_draft_assessment` (`backend/app/api/v1/questionnaire.py`), which defaults `last_viewed_category_id` to `None`. This means `lastViewedCategoryId === null` already reliably means "this is a fresh draft — first-ever visit OR a fresh retake, nothing to resume" (this is even documented in the existing code's own comment: "null for a first-ever visit"), and non-null already reliably means "resuming an in-progress draft partway through." **No backend change is needed** — this is exactly the CONTEXT.md-locked signal ("shown on every fresh assessment start... not shown when resuming an in-progress draft") and it already exists.

Render the welcome screen as an early return, before the `StepPills`/question-card layout:
```tsx
if (showWelcome) {
  return <WelcomeScreen onBegin={() => setShowWelcome(false)} />;
}
```
This satisfies every locked constraint for free: it sits outside `StepPills` (separate return branch, `StepPills` never renders), it's not counted in "Question X of Y" (that JSX branch never renders either), and it's one-way (nothing in the rest of the component ever sets `showWelcome` back to `true` — clicking "Previous" on Governance only decrements `categoryIndex`, which has no path back to the welcome branch).

**When to place this relative to the existing `if (submitted) {...}` early return:** either order works; placing it first is slightly more logical (a fresh draft cannot simultaneously be submitted).

### Anti-Patterns to Avoid
- **Making the welcome screen a new TanStack Router route** (e.g. `/questionnaire/welcome`): rejected by the locked decision ("a real step in the wizard flow... not a modal/overlay") which implies in-component state, not URL-level navigation — a new route would also need its own data-loading duplication (`config`/`initiativeId` already loaded by `questionnaire.tsx`) for no benefit.
- **Storing subsection names in a frontend-only TS constant keyed by an assumed stable array order**: works today (verified order is stable) but is more fragile than config-driven if a future phase reorders `config/dssc-questionnaire.json`'s questions — prefer the config-extension pattern above.
- **CSS-variable-only font swap**: changing only `--font-family` in `globals.css` will not visually change the ~20 files that hardcode `fontFamily: "'Open Sans', sans-serif"` inline per-element (inline styles always win over inherited CSS) — see Pitfall 4.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Gradient-clipped heading text | A custom SVG/canvas text renderer | Plain CSS: `background: linear-gradient(...); background-clip: text; -webkit-background-clip: text; color: transparent; -webkit-text-fill-color: transparent;` | Standard, well-supported CSS technique (needs the `-webkit-` prefixes for Safari) — no library needed |
| Variable-font loading | A JS font-loader library (e.g. FontFaceObserver) | Native `@font-face` with a `font-weight: 100 900` range + `font-display: swap` | Native CSS variable-font support has been universal across Chrome/Firefox/Safari/Edge since 2018; a JS loader adds nothing here since there's no FOUT-sensitive layout-shift concern beyond what `font-display: swap` already handles |
| Vite font-asset serving | A custom Vite plugin or manual `public/` wiring | Standard ES-module asset import: place the `.ttf` under `frontend/src/assets/fonts/` and reference it from `@font-face`'s `src: url(...)` in `globals.css` (a file already in the module graph via `main.tsx`'s `import './styles/globals.css'`) | Vite's official guidance: "Common image, media, and font filetypes are detected as assets automatically" and "In general, prefer importing assets unless you specifically need the guarantees provided by the public directory." This exactly mirrors how the two existing logo PNGs are already handled in this repo (`import logoSrc from '../assets/logo-dssc-color.png'`) |

**Key insight:** every piece of this phase is either plain CSS, plain React conditional rendering, or a JSON content edit. There is no algorithmic complexity or state-machine subtlety beyond the one `useEffect` gating issue documented in Pitfall 1 below.

## Common Pitfalls

### Pitfall 1: The existing `saveLastViewedCategory` effect will defeat the welcome-screen "fresh start" signal if not gated
**What goes wrong:** `WizardPage.tsx` (current, lines 231-233) has:
```tsx
useEffect(() => {
  saveLastViewedCategory(initiativeId, config.categories[categoryIndex].id);
}, [categoryIndex, initiativeId, config]);
```
This fires unconditionally on **every mount**, including the very first mount when the welcome screen should be showing. If left as-is, adding a `showWelcome` state on top of the existing code (without touching this effect) means: the effect writes `last_viewed_category_id = categories[0].id` to the server the instant `WizardPage` mounts — even while the welcome screen is the only thing visually rendered. A page refresh at that point would then re-fetch `lastViewedCategoryId` as non-null, and the component would compute `showWelcome = lastViewedCategoryId == null` as `false` — silently skipping the welcome screen after a mere refresh, before the user ever clicked past it.
**Why it happens:** the effect was written (Phase 15, D-08) before this phase's welcome-screen concept existed, and correctly assumed "mounting the wizard = the user is looking at a category page," which stops being true once a pre-category welcome state is introduced.
**How to avoid:** gate the effect's body (not the hook call itself — React's Rules of Hooks require the `useEffect` call to remain unconditional) on `showWelcome`:
```tsx
useEffect(() => {
  if (showWelcome) return;
  saveLastViewedCategory(initiativeId, config.categories[categoryIndex].id);
}, [categoryIndex, initiativeId, config, showWelcome]);
```
**Warning signs during manual verification:** refresh the page while the welcome screen is showing (before clicking "Begin") — if it jumps straight to Governance on the next load, this guard is missing.

### Pitfall 2: The About page's visible background is owned by `_app.tsx`, not `about.tsx`
**What goes wrong:** `frontend/src/routes/_app.tsx` (the shared layout for every authenticated route — dashboard, questionnaire, admin, About, etc.) sets:
```tsx
background: 'linear-gradient(90deg, rgba(118,184,42,0.1) 0%, rgba(118,184,42,0.1) 100%), white'
```
directly on its wrapping `<div>`. Both gradient stops are the same color, so this is actually a **flat solid tint**, not a real gradient — the exact anti-pattern the CONTEXT.md decision calls out avoiding for the homepage hero. `about.tsx` itself sets no background at all; whatever shows behind its 760px-wide content column today is this shared `_app.tsx` tint.
**Why it matters:** "give the About page dssc.eu's hero-style background wash" cannot be done by editing `about.tsx` alone — the planner must explicitly choose:
  - (a) change `_app.tsx`'s shared background to the dssc.eu wash → visually affects **every** authenticated page (dashboard, wizard, admin), which is broader than this phase's named scope ("Homepage & About page"), or
  - (b) leave `_app.tsx` untouched and give `about.tsx` its own local background (e.g. a full-bleed wrapper `<div>` around the About page's content with the dssc.eu wash, breaking out of `_app.tsx`'s `padding: 2rem` if a true full-bleed hero-style band is wanted, or simply a card/section-level tinted background if a full-bleed isn't necessary).
**Recommendation:** (b) — scope the background change to the About route only, to stay strictly within this phase's stated boundary; note the app-wide `_app.tsx` background as a candidate for a future, deliberately-scoped phase rather than an incidental side effect of this one.
**How to avoid:** flag this explicitly in the plan as a decision point, don't let it default silently to "touch `_app.tsx` because that's where the background lives."

### Pitfall 4: "Jost app-wide" requires a mechanical multi-file replace, not just a CSS variable change
**What goes wrong:** `globals.css` defines `--font-family: 'Open Sans', sans-serif` and `body { font-family: var(--font-family); }`, and `theme.ts`'s `mamiTheme.token.fontFamily` feeds antd's `ConfigProvider`. Updating *only* these two central definitions will **not** visually change most of the app, because a repo-wide grep found **126 occurrences of the literal string `'Open Sans'`/`"Open Sans"` across 20 files** (`WizardPage.tsx` alone has 13; `dashboard.tsx` 17; `initiative.tsx` 21; etc.) — nearly every custom component hardcodes `fontFamily: "'Open Sans', sans-serif"` inline per-element, and inline styles always win over inherited CSS and over antd's theme tokens for any element that isn't an antd component itself.
**Why it happens:** this codebase's established convention (visible in every file read during this research) is per-element inline `style={{}}` objects, not CSS classes or a shared style-constants module — so there is no single choke point that "Jost app-wide" can hook into today.
**How to avoid:** treat this as two separate, clearly-scoped edits:
  1. Update the two central definitions (`globals.css`'s `--font-family` var + `@font-face`/`@import` block, `theme.ts`'s `fontFamily` token) so anything that *does* inherit or consume them switches automatically.
  2. Do a deliberate, mechanical find-and-replace of the literal `'Open Sans'` (and `"Open Sans"`) substring → the new Jost stack across all 20 files found by `grep -rl "Open Sans" frontend/src` — this is large in file-count but trivial in per-occurrence risk (a pure string swap, no logic changes), and is the only way to make the change actually visible everywhere, matching the locked "app-wide" decision.
  Do **not** attempt to instead delete all inline `fontFamily` overrides and rely purely on CSS inheritance in this same phase — that's a much larger, higher-risk refactor (touches JSX structure, not just a string) for no additional visual benefit right now.
**Also drop the Google Fonts `Open Sans` import** once no file references it anymore — `globals.css`'s current `@import url('https://fonts.googleapis.com/css2?family=Jost:wght@500;600;700&family=Open+Sans:wght@300;400;600;700&display=swap')` pulls **both** fonts from Google's CDN today (interesting: Jost is already being loaded from Google Fonts, just not used consistently as the primary font stack) — this whole `@import` line should be removed and replaced by the self-hosted `@font-face` block, since self-hosting was the locked decision specifically to avoid the CDN dependency.

### Pitfall 5: `verbatimModuleSyntax: true` requires `import type` for the new `Subsection` type
**What goes wrong:** `frontend/tsconfig.app.json` has `"verbatimModuleSyntax": true`, which errors on default/non-type imports of type-only symbols under certain conditions.
**How to avoid:** follow the existing convention already used for `Category`/`Question` (e.g. `StepPills.tsx`: `import type { Category } from "../../lib/questionnaire";`) — import the new `Subsection` type the same way: `import type { Subsection } from "../../lib/questionnaire";`. This is not a new pitfall introduced by this phase, just a reminder to match the existing pattern exactly.
