<objective>
Close Gap 1 (HIST-01): the retake flow is shipped but provably non-functional end-to-end because nothing in the codebase ever resets `Initiative.status` from `submitted` back to `draft` after submission. A real user who submits, confirms "Start new assessment", and lands on `/questionnaire` gets a 403 "Submitted assessments cannot be edited" on the very first answer save, forever — the version-increment machinery this phase's migration exists for is unreachable through the UI.

This plan adds an explicit `POST /initiatives/{id}/retake` endpoint (the review's preferred option, and the natural fit for D-13's "explicit, confirmed user action") that atomically resets `Initiative.status` to `draft` and creates a fresh, blank, version-incremented draft Assessment. The dashboard's confirm dialog calls it before navigating.

Purpose: make the retake half of the phase goal ("Retaking the questionnaire creates a new, dated assessment version") actually hold true through the real UI/API path.
Output: new retake endpoint, wired dashboard confirm dialog, and a real end-to-end test exercising POST /submit -> POST /retake -> PUT answer.
</objective>

Because submit_initiative already flipped the prior draft to submitted, no draft exists, so the helper computes `version = max(existing) + 1` and inserts a new blank draft (D-14: no answers carried forward, D-15: version incremented). The helper performs its own commit, which atomically persists the initiative.status reset added in step 3 within the same session/transaction.
    5. Return a small JSON dict: `{"message": "New assessment started", "version": assessment.version, "assessment_id": assessment.id}`.

    Do NOT copy any answers from the prior version (D-14 — retake starts fully blank). Do NOT add a completion gate here.
