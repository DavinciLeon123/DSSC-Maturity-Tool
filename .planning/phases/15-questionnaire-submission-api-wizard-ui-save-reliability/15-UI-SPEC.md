# Phase 15 — UI Design Contract

> Visual and interaction contract for the rebuilt questionnaire wizard (QSTN-02), save-reliability UX
> (SAVE-01–04), and retake/history views (HIST-01/02). Generated by gsd-ui-researcher, verified by
> gsd-ui-checker. Behavioral decisions (D-01 through D-17) already locked in
> `15-CONTEXT.md` are treated as inputs here, not re-litigated — this file adds the pixel/copy/state
> layer on top of them.

## Design System

| Property | Value |
|----------|-------|
| Tool | none — no `components.json`/shadcn anywhere in this repo. This is a pre-existing production app already committed to **antd v6** as its component library (`frontend/package.json`), with a real, wired theme (`frontend/src/lib/theme.ts` → `ConfigProvider`). Introducing shadcn mid-project would fragment an established system rather than fill a gap, so the shadcn init gate is deliberately **not** invoked this phase. |
| Preset | not applicable |
| Component library | antd v6 (`Card`, `Button`, `Alert`, `Input`, `Select`, `Tag`, `Modal`, `Grid.useBreakpoint`) — reuse these primitives for any new chrome (history table, confirmation dialog, error banners) rather than hand-rolling new ones. Bespoke `div`/`button`-with-inline-`style` is the existing convention specifically for the wizard's question-card surface (`WizardPage.tsx`, `QuestionCard.tsx`, `AnswerButtonGroup.tsx`, `StepPills.tsx`) — continue that convention for the rebuilt radio-scale/progress/badge, since it is already the dominant pattern in this exact subtree. |
| Icon library | none installed as a standalone package. `@ant-design/icons` ships transitively inside antd v6 and is already used implicitly by `<Alert showIcon>`/`Modal.confirm`. The wizard subtree's own convention is literal Unicode glyphs (`✓`, `→`, `×`) with no icon font at all (`StepPills.tsx`, `WizardPage.tsx`). **Continue the glyph convention** for any new iconography this phase needs (retry icon, checkmarks) — do not add `@ant-design/icons` as an explicit new dependency for this phase's scope. |
| Font | Rubik (Google Fonts, `frontend/src/styles/globals.css` `@import`), applied via `fontFamily` in both `theme.ts` (antd-wide) and inline `fontFamily: "'Rubik', sans-serif"` throughout the wizard subtree. Keep the inline-fontFamily convention on any new bespoke (non-antd) element — antd components inherit it automatically via `ConfigProvider`. |

**Known token drift (pre-existing, not introduced by this phase — do not propagate the wrong side of it):**
`frontend/src/styles/globals.css` defines CSS custom properties (`--color-navy: #020059`, `--color-green: #41A765`, `--border-radius-sm: 6px`, `--border-radius-lg: 30px`) that **do not match** the actual wired antd theme (`theme.ts`: `colorPrimary: '#06004f'`, `colorSuccess: '#399e5a'`, `borderRadius: 8`, `borderRadiusLG: 16`). Only 4 files reference the CSS vars (`QuestionCard.tsx`, `FollowupPanel.tsx`, `ContextCallout.tsx`, `Sidebar.tsx`) vs. 17+/13+ call sites using the correct literal hex directly. Since `QuestionCard.tsx` is a direct rebuild target this phase (QSTN-02) and `FollowupPanel.tsx`/`ContextCallout.tsx` are being dropped (see Component Inventory below), **this phase is the natural point to stop the drift**: use the literal hex values from `theme.ts` (`#06004f` navy, `#399e5a` green, `8px`/`16px` radius) directly, matching the dominant existing convention — do not add new `var(--color-navy)`/`var(--border-radius-sm)` usages.

## Spacing Scale

Declared values (must be multiples of 4) — matches the existing wizard subtree's convention exactly (`0.5rem`/`0.75rem`/`1rem`/`1.5rem`/`2rem`/`2.5rem`/`4rem` = 8/12/16/24/32/40/64px, all already multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-text gaps (e.g. step-pill dot to label) |
| sm | 8px | Compact spacing (badge padding, gap between radio circle and its label) |
| md | 16px | Default element spacing (question card internal gaps, form field spacing) |
| lg | 24px | Section padding (space above nav buttons, category header margin) |
| xl | 32px | Layout gaps (wizard's progress-panel ↔ question-card gap) |
| 2xl | 48px | Major section breaks (submitted-confirmation page vertical rhythm) |
| 3xl | 64px | Page-level spacing (submitted-confirmation page top/bottom padding) |

Exceptions:
- **44px minimum touch/hit target** on every interactive control this phase introduces or resizes — the radio-scale's 5 circles, the Retry button, the Next/Back/Submit buttons, and the "Start new assessment" button. This matches the already-wired antd theme (`theme.ts` → `Button`/`Input` `controlHeight: 44`) and WCAG 2.5.5 (Target Size). The *visible* circle for the radio-scale can render smaller (28–32px) than its clickable hit area — pad the click target to 44px rather than growing the visual circle, to keep 5 options readable in one horizontal row on a 1100px-max wizard card.
- **2.5rem (40px) card padding** on the outer question-card container is an existing, already-multiple-of-8 exception (not a new one) — keep it as-is (`WizardPage.tsx` line ~483).

## Typography

Scoped to this phase's new/rebuilt surfaces (radio-scale, progress indicator, autosave/retry, history page). Pre-existing page-level headings elsewhere in the app already use a 700-weight/28px convention outside this phase's scope — that convention is inherited, not reopened, here.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Micro / badge / helper | 13px (0.8125rem) | 500 | 1.4 |
| Body / question text / option label | 16px (1rem) | 400 regular · 600 selected/emphasis | 1.5 |
| Category / section heading | 20px (1.25rem) | 600 | 1.2 |
| Page-level heading (history page title, submitted-confirmation) | 28px (1.75rem) | 700 *(existing app-wide convention, inherited — not a new weight introduced by this phase)* | 1.2 |

Declared weights for **new** work this phase: **400 (regular)** and **600 (semibold)** — used for the option-label unselected/selected states, question text, category headings, and table content. The 700 weight above is pre-existing and used only for full-page headings, matching every other page in the app (dashboard `h1`, submitted-confirmation `h2`) — not introduced net-new by this rebuild.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#FFFFFF` | Question-card surface, progress-panel surface, history-table surface, modal background |
| Secondary (30%) | `rgba(57,158,90,0.1)` (page/layout wash, existing `theme.ts` `colorBgLayout`) + `rgba(6,0,79,0.08)` (hairline dividers/borders between sections) | Page background behind the wizard/history cards; thin borders (nav-button divider, table row separators) |
| Accent (10%) | `#06004f` (navy) | Reserved for: primary CTA buttons (Next / Submit assessment / Start new assessment), the active step-indicator circle, the selected radio circle's border+fill when *not yet saved*, links, focused input borders. Never used for plain body text emphasis beyond headings. |
| Second semantic (positive/success) | `#399e5a` (green) | Reserved for: the "Saved ✓" autosave badge state, completed step-indicator circles/checkmarks, the selected radio circle once its save has confirmed, the "Submitted" status tag. This is a second brand color already established app-wide (`theme.ts` `colorSuccess`) — kept distinct from the navy accent above, not folded into it. |
| Destructive / blocking-error | `#991B1B` text on `#FEE2E2` background | Reserved for: the *terminal* (retries-exhausted) autosave-failed state, the inline "this answer didn't save" banner that blocks Next/Submit (D-10/D-11/D-12), the history-list load-failure banner. Matches the exact existing hex pair already used for `submitError`/`reportError` in `WizardPage.tsx` — reuse verbatim, do not introduce a new red. |
| Transient warning | `#F59E0B` | Reserved for: the *in-progress auto-retry* badge state ("Save failed — retrying") and the rate-limited badge state ("Too many saves — slow down") — both **self-healing**, not yet blocking. Keep visually distinct from the destructive red above; this distinction is load-bearing for D-09 (auto-retry-then-manual-retry sequencing) so a user can tell "still trying" apart from "action needed." |

Accent reserved for: primary CTA buttons, active step indicator, selected-but-unsaved radio circle, links, focused inputs — **never** the default/idle state of every button or every radio circle (that stays neutral/white with a subtle border, per the existing `AnswerButtonGroup.tsx` unselected style).

## Component Inventory

**Rebuild (schema-breaking — old shape no longer matches the backend at all):**
- `frontend/src/lib/questionnaire.ts` — full rewrite: drop `AnswerValue = "YES"|"NOT_THERE_YET"|"NOT_APPLICABLE"`, `mami_code`, `Followup`, `Topic`; new shape follows `config/dssc-questionnaire.json` (`version`, `categories[{id, name, questions[{id, category_id, text, options?}]}]`, `default_options`) and the live backend `AnswerCreate`/`AnswerRead` (`question_id`, `category_id`, `score: 1-5`).
- `frontend/src/components/questionnaire/AnswerButtonGroup.tsx` → becomes the new **radio-scale** component (QSTN-02): 5 options in a **horizontal row** (not today's vertical stack), each a circle + label, mapped from `question.options ?? default_options` (label→score 1-5). Keep the existing selected/unselected visual language (filled circle + inner dot on selection, border-color swap) — just re-lay-out horizontally and drive labels/count from config instead of the hardcoded 3-item array.
- `frontend/src/components/questionnaire/QuestionCard.tsx` — rebuild: drop the `showFollowup`/`FollowupPanel` branch entirely (new schema has no `followup` field on a question at all) — a question is now just question text + the radio-scale.
- `frontend/src/components/questionnaire/WizardPage.tsx` — rebuild per D-01–D-12: per-answer debounced save (not per-topic-on-Next), real retry wiring on `AutosaveBadge`, `beforeunload` forced-flush, resume-at-last-category (D-08), Next/Submit blocking on unsaved/failed state (D-10/D-12).
- `frontend/src/components/questionnaire/StepPills.tsx` — extend, don't replace: keep the category-stepper visual language (numbered circles → checkmark on complete), add the overall "N of 52 answered" counter (D-04) as a new small element near the top of the panel (below "Your progress," above the category list).

**Drop (orphaned by the new config schema — no code path can populate their props anymore):**
- `frontend/src/components/questionnaire/ContextCallout.tsx` — the new `config/dssc-questionnaire.json` categories have no `context_text`/`context_image` fields at all (only `id`/`name`/`questions`). Confirm-delete during planning rather than leaving a permanently-`null`-props dead component.
- `frontend/src/components/questionnaire/FollowupPanel.tsx` — the new question shape has no `followup` field; this component has no caller once `QuestionCard.tsx` is rebuilt.
- `frontend/src/components/questionnaire/FindingsPanel.tsx` — **pre-existing orphan, not created by this phase**: already has zero importers today, and its prop type (`ScoreResponse` from `frontend/src/lib/scoring.ts`: `findings`/`critical_count`/`severity`) doesn't match the real Phase-14 backend response shape (`{initiative_id, dimension_scores}`) at all. Flagging for planner awareness since it sits in the same directory as this phase's other rebuild targets, but its removal is not required by any Phase 15 requirement — safe to leave for Phase 16/17 cleanup if out of this phase's file list.

**New (greenfield, per D-16/D-17):**
- History page/route (`/assessments` or `/history` — exact path is planner's discretion per `15-CONTEXT.md`): two stacked sections — (a) a list/table of past submitted assessment versions (date, version #, overall average, link-out), (b) a per-dimension comparison table across versions. Both are plain antd `Table` (or equivalent) usage — no chart, per D-16's explicit "boring tabular" scope boundary (Phase 16 owns the radar/priority visualization).
- `frontend/src/routes/_app/dashboard.tsx` — add a `View assessment history` link/button beside the existing Start/Retake button (D-17), and wrap the existing "Start/Retake Questionnaire" click-through in the new confirmation dialog when `initiative.status === "submitted"` (D-13) — the first-ever-draft case (no prior submission) still navigates straight through with no dialog, since there is nothing to confirm overwriting yet.

**Reused as-is (no visual change needed):**
- `AutosaveBadge`'s existing 5-state model (`idle/saving/saved/failed/rate-limited`) — extend its wiring (real retry, terminal-vs-transient distinction within `failed`), not its visual states.
- antd `Card`/`Button`/`Alert`/`Tag` conventions already established in `dashboard.tsx` for any new dashboard-level chrome (history link, confirmation dialog trigger).
